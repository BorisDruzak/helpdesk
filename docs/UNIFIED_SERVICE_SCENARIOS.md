# Единая студия услуг: руководство администратора

Услуга создаётся и редактируется через карту сценария. Простая форма — карта
«Начало → вопрос → результат». Раздел — крупная область помощи, категория —
необязательная папка, услуга — одна поддерживаемая карта. Точки входа этой карты
отображаются сотруднику как разные пункты каталога. Например, одна услуга
«Печать» может иметь входы «Не печатает» и «Замятие бумаги».

## Создать простую услугу

1. Откройте **Каталог услуг**. Выберите раздел или категорию слева.
2. Нажмите **Создать услугу**. Откроется карта с блоком **Начало**.
3. В настройках карты задайте **Название услуги**. Раздел и категория наследуются
   от выбранного места каталога; категория необязательна. Описание можно раскрыть.
4. В библиотеке нажмите **Вопрос**. Выберите блок и задайте **Что спросить?**,
   **Тип ответа**, при необходимости **Обязательный ответ** и подсказку.
5. Протяните связь от зелёной точки справа у **Начало** к точке слева у вопроса.
   На пунктирной линии появится название входа. Нажмите на него и введите понятное
   сотруднику название, например «Не печатает принтер». Эта связь создаёт пункт
   каталога; она не выполняет шаг сценария. Альтернатива для клавиатуры:
   настройки карты → **Подключить вход с клавиатуры** → первый шаг.
6. Нажмите **+ Добавить следующий шаг** в вопросе и выберите результат создания
   обращения. Кнопка добавит блок и связь. Можно добавить результат из библиотеки
   и протянуть обычную стрелку вручную.
7. Нажмите **Сохранить черновик**. Черновик не становится доступен сотрудникам.
8. Нажмите **Тестировать**, заполните ответы и пройдите до результата. Проверьте
   очередь, рассчитанный приоритет и сроки. Тестирование не создаёт обращение.
9. Нажмите **Опубликовать**, прочитайте проверку и изменения, подтвердите публикацию.
   Если есть ошибки, исправьте отмеченный вопрос, переход или обработку.

Перед отправкой сотрудник автоматически получает сводку ответов. Отдельный блок
сводки добавлять не нужно. Сервер сохраняет проверки, права и согласования.

## Пять видов блоков

| Блок | Что настроить | Когда использовать |
|---|---|---|
| Вопрос | Текст, тип ответа, варианты, обязательность | Собрать сведения о проблеме |
| Инструкция | Заголовок, текст действий, подтверждение прочтения | Предложить сотруднику решение |
| Условие | Условия исходящих стрелок, ветка «иначе» | Выбрать путь по уже собранным ответам |
| Проверка результата | Вопрос о результате, ветви «Да», «Нет», «Не знаю» | Проверить, помогла ли инструкция |
| Результат | Создать обращение либо завершить без обращения | Завершить маршрут |

Старые блоки сводки и диагностики сохраняются в существующих картах. Диагностика
Endpoint не доступна в обычной библиотеке до включения соответствующего backend.

## Создать ветвящийся сценарий

1. Добавьте вопрос с типом **Да / нет**, **Один вариант** или **Список**. Для списка задайте варианты.
2. Добавьте **Условие**, соедините вопрос с ним.
3. Условие сразу показывает связанный вопрос и его ответы. Нажмите **+ Шаг** у
   **Да**, **Нет** или другого варианта прямо на блоке и выберите следующий шаг.
   Для второй ветви повторите действие у другого ответа: получится отдельный путь,
   а не вставка внутрь первой ветви. Заранее создавать следующие блоки не нужно.
4. В инспекторе условия раздел **Ветвление по ответам** позволяет выбрать
   **Вопрос для ветвления**, добавить шаг для ответа или выбрать существующий
   **Следующий шаг**. По умолчанию выбран ближайший входящий вопрос с вариантами;
   доступны и предыдущие вопросы на входящих маршрутах. Выбор источника меняет
   только предлагаемые новые ветви, сохраняя уже настроенные переходы.
   Ответ также можно соединить с входом существующего блока линией.
   Для сложных правил в **Куда идти дальше** добавьте условную ветвь и настройте
   **Если**. Настройку можно открыть нажатием на стрелку. Для запасного пути выберите
   **Иначе**, раскройте её и задайте **Если ни одно условие не выполнено**.
   Оставьте только один путь «иначе».
5. Соедините конечные пути с результатами. Проверяйте все варианты в тестировании.

Условие не спрашивает сотрудника повторно: оно проверяет ответ предыдущего вопроса.
«Нет» — явный отрицательный ответ. Если вопрос пропущен или ответ неизвестен,
настройте отдельный путь **Иначе**; отсутствие ответа не превращается в «Нет».
Для **Нескольких вариантов** каждая предлагаемая ветвь проверяет наличие своего
варианта в ответе. Несколько таких ветвей могут подойти одновременно; действует
обычный порядок и приоритет ветвей.
Нажмите на заголовок ветви, чтобы раскрыть или свернуть её настройки. В заголовке
остаются вопрос, сравнение, ответ и следующий шаг. **Развернуть все ветви** и
**Свернуть все ветви** управляют всей панелью, не изменяя карту. Новая ветвь
раскрывается автоматически.

Следующим блоком может быть другое **Условие**: соедините блоки на карте либо
выберите его в **Следующий блок** раскрытой ветви или в **Иначе**.
Чтобы добавить новое условие в существующий путь, нажмите **+** на нужной стрелке
и выберите **Добавить условие**. Условие исходной связи сохраняется, а прежнее
продолжение становится ветвью **Иначе** нового блока. Затем добавьте ему нужные
условные ветви. Циклические связи запрещены.

В карточке вопроса на карте указан его тип. Изменить его можно в **Тип ответа**:
например, **Короткий текст**, **Список**, **Один вариант**, **Несколько вариантов**.
В расширенных настройках вопроса можно отдельно задать **Когда показывать вопрос**
и **Когда ответ обязателен**. Проверки длины/числа ограничивают допустимый ответ.

## Создать маршрут самостоятельного решения

1. Вопрос → инструкция → проверка результата.
2. От проверки проведите первую связь к результату «завершить без обращения».
   Новая карта назначает ей ветвь **Да**.
3. Вторую связь проведите к созданию обращения — ветвь **Нет**.
4. При необходимости добавьте третью связь **Не знаю**. Проверьте условия стрелок.
5. В результате без обращения задайте сообщение сотруднику.

## Несколько пунктов каталога для одной услуги

Соедините **Начало** с ещё одним подходящим блоком. На каждой пунктирной линии
задайте своё название. Нажмите линию для настройки описания, поисковых слов,
видимости и включения входа. Поисковые слова необязательны; категория наследуется
от карты. Несколько входов могут сходиться в общий маршрут. Начало нельзя удалить.

Чтобы переместить вход, переподключите конец пунктирной линии к другому блоку.
Чтобы удалить пункт каталога, выберите линию и удалите вход в инспекторе. Удаление
входа из черновика не переключает опубликованную версию до новой публикации.

## Влияние ответов и ветвей на обработку

У вопроса с фиксированными вариантами или ответом «Да / нет» раскройте
**Влияние ответов на обработку**. Для нужного ответа задайте:

- **Масштаб воздействия**: один пользователь, несколько пользователей, подразделение.
- **Срочность**: работа продолжается, работа затруднена, работа остановлена.
- **Важность**: обычный, важный или критичный процесс.

Влияние отдельной ветви задаётся в инспекторе её стрелки. Пустое значение не вносит
дополнительного влияния. По пройденному пути учитывается максимальное значение
каждого измерения. Скрытые вопросы и отброшенные после возврата ответы не влияют.
Ответ «Не знаю» не превращается в «Нет».

Приоритет рассчитывает сервер по действующим политикам. Если правило не принимает
нужное измерение, проверка публикации покажет ошибку. Для исторических v1/v2
**Обработка услуги** сохраняет выбор существующих опубликованных правил.

### Собственные сроки и направления карты v3

Новые карты используют `schema_version: 3`. В **Обработка услуги** настройте
**Сроки обработки**: создайте именованные профили, задайте первый ответ и решение,
единицы времени и календарное либо рабочее время. Для рабочего времени выберите
действующий рабочий календарь. Сроки принадлежат этой карте и входят в её
опубликованную версию; изменение другой карты их не меняет.

В **Куда направлять обращения** создайте понятные имена направлений и выберите
действующие очереди. Назначьте стандартный профиль и направление карты. Пустые,
недоступные или неверные настройки блокируют публикацию с объяснением.
Создавать отдельные общие политики маршрутизации и SLA для новой карты не нужно.

В инспекторе стрелки или ветви условия выберите следующий блок, направление и
профиль SLA. Назначение сохраняет параметры будущей заявки: диагностика ещё не
создаёт и не переназначает обращение. Последующая выбранная ветка может заменить
очередь или профиль; порядок задаёт пройденный маршрут, а проверка показывает
источник и заменённое значение. Без назначений ветвей действуют явные значения
карты по умолчанию. Приоритет P1 сам по себе не задаёт срок: срок определяет профиль.

Один блок **Условие** может проверять ответы трёх и более предыдущих вопросов.
Используйте **Все условия**, **Любое условие**, группы и отрицание. Источники
выбираются по названиям вопросов. Если специализированный вход пропускает вопрос,
его ответ может отсутствовать: используйте проверку **Ответ задан** и понятную
ветвь **Иначе**. Неизвестное значение не равно ответу «Нет». Пересекающимся
правилам нужен явный порядок, показанный в редакторе.

При добавлении условия для вопроса со списком вариантов редактор сразу предлагает
**Равно** и варианты этого вопроса; для нескольких ответов — **Один из**. При смене
источника используются варианты выбранного вопроса. Правило **Ответ задан** можно
выбрать отдельно: оно проверяет наличие ответа и не требует выбора значения.
Сохранённые правила не меняются автоматически при открытии карты.

В v3 обязательный вопрос «Да / нет» требует явного ответа: «Нет» считается
ответом, пропущенный необязательный вопрос остаётся без значения. Старые карты
сохраняют прежнюю семантику флажков. Рабочее расписание закрепляется при публикации;
отключённый календарь блокирует новую отправку, а редактирование расписания не
меняет уже закреплённые сроки карты.

Серверная проверка показывает маршрут, ответы, результаты частей условий,
очередь, профиль/сроки, приоритет и необходимость согласования. Сравните два
прогона с разными ответами. Проверка не создаёт заявку и не отправляет согласование.
Реальное создание использует те же канонические сервисы и повторно проверяет
доступность очереди и настроек; согласование выполняет штатная система Helpdesk.
Согласующие определяются действующим правилом согласования услуги. Для источника
«руководитель» сервер использует проверенную связь сотрудника и руководителя в
реестре и канонический UI-аккаунт согласующего. Если источник недоступен, применяется
явно настроенный резервный источник либо проверка останавливает отправку.

В настройках раздела каталога **Правила обработки новых услуг** позволяют выбрать
«Как для …» существующей услуги. Это задаёт серверный образец обработки. Если
раздел имеет несколько разных правил и образец не выбран, сохранение новой услуги
попросит определить его. Внутренние шаблоны и ключи для этого знать не нужно.

## Кнопки карты и каталога

| Действие | Результат |
|---|---|
| Каталог / вернуться к услуге | Возврат; несохранённые изменения защищены предупреждением |
| Сохранить черновик | Сохраняет карту с проверкой серверной ревизии |
| Тестировать | Прогон маршрута и обработки без создания заявки |
| Опубликовать | Проверка маршрутов и подтверждённое переключение активной версии |
| Версии | История; восстановление версии создаёт черновик, не переключает её сразу |
| Отменить / повторить изменение | История локальных изменений карты |
| Вся карта | Показывает весь граф |
| Начало маршрута | Приближает начало маршрута |
| Предпросмотр страницы | Оформление страницы сотрудника; ответы здесь не сохраняются |
| Как у сотрудника | Предпросмотр выбранного блока в инспекторе |
| Свернуть библиотеку / настройки | Освобождает место для карты |
| Настройки карты | Название, размещение, описание, наследуемая обработка |
| + в блоке / на стрелке | Добавляет и соединяет новый шаг |
| Копировать блок | Создаёт отдельную копию выбранного блока |
| Удалить блок | Показывает затронутые связи/входы и варианты их разрешения |
| Поиск / состояние / сортировка | Находят услуги; не меняют карту |
| + структуры каталога | Создание раздела; меню папки управляет категорией |

Перемещение блоков меняет только координаты. Связи не должны тянуть другие блоки.
Циклические исполняемые маршруты запрещены; сотрудник возвращается штатной кнопкой
назад. При конфликте ревизий локальные изменения остаются в редакторе: загрузка
серверной версии заменит их, поэтому сначала сохраните нужный текст отдельно.

## Правила обработки услуги

На карте нажмите **Обработка услуги** слева. Эти настройки относятся ко всем
обращениям этой услуги. Приоритет, очередь и сроки вычисляет существующий серверный
механизм. В v3 очередь и профиль сроков выбираются из карты по пройденным ветвям;
остальные политики и исторические v1/v2 продолжают использовать действующие правила.

**Закрытие обращения** определяет необходимые данные и подтверждения завершения.
**Видимость обращения** определяет поля и статусы, доступные сотруднику после создания
обращения; это не доступность самой услуги в каталоге.

**Использовать действующие правила** сохраняет серверное наследование, но не создаёт
недостающую политику. Если проверка публикации сообщает об отсутствии правила,
нажмите **Исправить**: откроется отдельный экран обработки, нужное поле будет первым
и получит фокус. Выберите подходящее опубликованное правило, сохраните черновик и
повторите **Опубликовать → Подготовить публикацию**. Кнопка **К настройкам услуги**
возвращает к названию и категории. Проверка и навигация не меняют карту сами.

У **Закрытия обращения** и **Видимости обращения** доступны **Создать правило**
и **Настроить выбранное**. Они открывают настройки прямо поверх карты услуги:

1. Задайте понятное название правила и заполните поля. Закрытие определяет
   обязательные итоги, подтверждения и срок автозакрытия; видимость — публичные
   названия статусов, доступные и скрытые поля.
2. Нажмите **Проверить и продолжить**, проверьте настройки и **Опубликовать правило**.
   Сервер использует существующий реестр и проверку политик.
3. Нажмите **Применить к услуге**. Ссылка на правило попадёт в черновик карты;
   включённое автосохранение сохранит черновик. Проверьте статус сохранения.
   Само правило не меняет действующую услугу через наследование.
4. **Сохранить черновик → Тестировать → Опубликовать → Подготовить публикацию**.
   После успешной проверки подтвердите публикацию услуги штатной кнопкой.

Настройка выбранного правила сохраняет отдельную копию для услуги, включая
дополнительные существующие параметры. Общий исходный вариант не изменяется.
Закрытие окна защищает внесённые изменения; при ошибке сервера настройки остаются
в окне. Неопубликованные настройки хранятся только до закрытия редактора/вкладки.

## JSON и YAML

Раскройте **JSON / YAML** под картой. Сначала сохраните карту.

- Экспортируйте JSON или YAML: оба представляют ту же карту.
- Для импорта выберите формат и файл либо вставьте текст.
- Нажмите проверку: сервер покажет ошибки и изменения без сохранения и публикации.
- Примените проверенный документ в редактор, затем сохраните обычный черновик.
- Импорт не может подменить привязку существующей услуги. Повторная публикация
  проходит те же проверки, что изменения мышью.

Для ошибок структуры и ссылок панель показывает путь рядом с объяснением,
например `processing.routes.workplace.queue_code`. Исправьте указанный параметр
и повторите проверку: применение документа доступно после устранения ошибок.

Полный пример v3: [guided-request-v3-equipment.yaml](examples/guided-request-v3-equipment.yaml).
Машинный контракт для генераторов: [JSON Schema](contracts/request-scenario.schema.json)
(Draft2020-12, версии1/2/3). Для нового документа задайте `schema_version: 3`.
Схема описывает черновик: пустые назначения/нулевые ещё не заполненные сроки можно
сохранять, но сервер не разрешает исполнение и публикацию до заполнения настроек.
Граф, активность очередей/календарей и все допустимые исходы дополнительно проверяет
сервер; структурная JSON Schema не заменяет эту проверку.

Обновить контракт после изменения DTO:
`python scripts/export_request_scenario_schema.py --output docs/contracts/request-scenario.schema.json`.
Проверить отсутствие дрейфа: та же команда с `--check`.

Перед импортом сопоставьте `service_code`, `offering_full_code`, внутренний
`request_template_key` и коды очередей с действующим каталогом вашей среды.
Пример не создаёт очереди или политики. Вход «Проблемы с печатью» намеренно
пропускает первый вопрос: неизвестный тип проблемы идёт по запасному пути.
Данные о названии, описании и поисковых выражениях входов публикуются вместе с картой.

## Поиск проблемы сотрудником

Поиск доступен по всему открытому сотруднику каталогу до выбора раздела.
Результат показывает конкретную проблему, её размещение, описание и способ
помощи; открывается выбранный пункт входа. Поиск учитывает регистр, `е/ё`,
пунктуацию, порядок слов, русские окончания, префиксы, настроенные выражения,
ограниченные опечатки и ошибочную раскладку. Точное название выше нечёткого
совпадения. Отрицание «не» сохраняется. При отсутствии совпадений доступны
подсказки и обычный выбор другой проблемы. Выбор всегда подтверждает сотрудник.
Скрытые, неопубликованные и недоступные услуги не участвуют в результатах.

Существующие ключи сохраняют ссылки между вопросами и условиями. Ручная правка
декларации — расширенная возможность; обычное создание не требует знания ключей.
Не поддерживаются дубли ключей, YAML aliases/anchors/custom tags, неизвестные версии,
нечисловые координаты и документы свыше допустимых ограничений.

## Перенос существующих форм

У сотрудника отображается опубликованная версия услуги; предпросмотр на карте
показывает текущий черновик. До публикации они могут различаться. Формы помощи
с профилем и привязкой компьютера доступны без агента и незаполненного профиля.
Остальные формы доступны без агента, если их политика это разрешает. Требование
заполнить профиль — отдельное серверное правило. Если оно отключено сервером,
интерфейс не должен скрывать обычные формы из-за неполного профиля.

Ошибка загрузки кабинета, каталога или формы показывается явно с кнопкой
**Повторить загрузку**. Фоновое обновление контекста сохраняет открытую форму
и введённые ответы. Ошибка доступа не превращается в сообщение о неполном профиле.

В каталоге раскройте **Перенос существующих форм**, нажмите **Проверить перенос**.
Отчёт разделяет готовые формы, уже существующие карты и неподдерживаемые особенности.
**Создать проверенные черновики сценариев** создаёт простые карты, сохраняя поля,
условия и обработку. Затем откройте карту, проверьте и опубликуйте обычным действием.

Перенос не удаляет формы, шаблоны и опубликованные версии. Не переключает действующие
услуги автоматически. Неподдерживаемые особенности явно указаны; такую услугу нельзя
считать перенесённой. Повторный запуск не перезаписывает существующие карты, включая
архив. Старые обращения и начатые сеансы продолжают использовать прежние версии.
Исторические карты версии 1 сохраняют свой формат при перемещениях/редактировании:
это совместимость, а не второй способ создания новой услуги. Кнопка **Перевести карту на единую модель** обновляет только черновик исторической карты; вопросы исторической карты редактируются после этого действия. Затем обязательны обычные тестирование и публикация.

## Реализация и эксплуатация

Регрессии каталога, сохранения с ревизиями, конфликта правок и доступа аудитора:
`pnpm --dir webapp exec vitest run src/app/router.test.tsx src/pages/admin/request-template-studio-catalog.test.tsx src/pages/admin/service-create-page.test.tsx --maxWorkers=1`.
Тесты используют карту версии 2 и её название услуги. Старый адрес создания услуги
проверяется как перенаправление в Студию с `create=1`, без самостоятельного сохранения
формы; параметры каталога сохраняются, запись истории браузера заменяется.

Браузерные регрессии: `pnpm --dir webapp exec playwright test tests/guided-studio.spec.ts tests/guided-studio-usability.spec.ts`.
Они проходят создание услуги сразу на карте, связи входов и условий, независимое
сворачивание ветвей, локальный предпросмотр без записи, права аудитора, сохранение,
подтверждение публикации и восстановление версии. Проверки прежнего мастера и
выбора формы или карты заменены проверками единой модели и старого адреса создания
услуги. Отдельная проверка совместимости внутренней публикации шаблонов сохранена.
Перед публикацией запускайте весь fixture-набор: `pnpm --dir webapp exec playwright test`.
Файлы `catalog-services`, `guided-category-inline`, `guided-processing`,
`guided-diagnostics` и `guided-sections` также проверяют новый каталог и навигацию;
историческое имя тестового файла не означает наличие прежнего мастера в продукте.

Каноническое хранение остаётся RequestStudioDraft.definition и неизменяемые версии
RequestStudioScenarioVersion.definition. Версия 2 декларации добавляет типизированные
эффекты. Сервер формирует виртуальную FormSchema из видимых вопросов пройденной карты
при preview/submit; независимая схема старого шаблона не определяет вопросы v2.
RequestTemplate используется только для существующей обработки. Отдельных таблиц
конфигурации и движка политик нет. Старые сеансы версии 1 сохраняют прежнюю валидацию.

API администратора: POST /api/web/admin/request-studio/services; POST /convert-forms;
POST /documents/validate; GET /scenarios/{id}/document?format=json|yaml. Они используют
существующие права, сохранение с revision/CAS, аудит и подтверждение публикации.
Импорт проверяет документ без записи. PyYAML 6 нужен для YAML; JSON хранится как прежде.
Миграция 149 после 148 расширяет CHECK версии до 1/2; старые строки не переписывает.
Откат ограничения запрещён, пока существуют неизменяемые опубликованные версии 2.

## Понятные поля правил закрытия и видимости

В **Обработка услуги → Создать правило** все поля имеют русские названия и пояснения.
«Запись о выполненной работе» означает запись поддержки в журнале обращения.
«Подтверждение выполнения диагностики» требует подтверждающий материал, когда
диагностический модуль использовался. «Подтверждение согласования» требует принятое
согласование, если оно применялось. Для отдельных приоритетов можно потребовать
подтверждающие материалы независимо от запуска диагностики.

**Допустимые результаты решения** — флажки с понятными названиями вместо кодов.
Пустой список не ограничивает результаты этим правилом. **Закрыть автоматически
через (дней)** задаёт ожидание после предложения решения; 0 отключает автозакрытие.

В видимости для каждого этапа задаётся название статуса, которое увидит сотрудник.
Это меняет подпись, а не переходы статусов. Списки **Показывать сотруднику** и
**Дополнительно скрывать от сотрудника** используют названия полей вместо ключей.
Скрытие и серверные права имеют приоритет. Внутренние заметки и подробная диагностика
защищены сервером независимо от флажков. Ранее настроенные дополнительные значения
сохраняются, даже если в новом интерфейсе для них нет отдельного переключателя.
