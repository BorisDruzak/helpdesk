# Техническое задание — Helpdesk Guided Request Studio v3

## 1. Цель

Переработать существующую Guided Request Studio в полноценную визуальную Low-Code систему настройки пользовательских обращений.

**Главная концепция:** администратор создаёт общую карту диагностики, добавляет в неё вопросы, инструкции, условия, проверки и результаты, а затем назначает отдельные участки этой карты точками входа из пользовательского каталога.

Одна карта может обслуживать множество пользовательских проблем без копирования диагностической логики.

Все настройки должны выполняться преимущественно непосредственно на карте сценария через контекстный инспектор выбранного элемента.

### Исходные материалы

- Репозиторий: https://github.com/BorisDruzak/helpdesk
- Исходная реализация Guided Request Studio: PR #41, merge `bb8c521faaf76eea01119f314f68fecdeb34cefb`.
- Существующий отдельный Product Design frontend-прототип Studio v3.
- Последняя утверждённая визуальная концепция: редактор карты с контекстным инспектором, точками входа из каталога, предпросмотром сотрудника и редактируемыми связями.
- Существующие Service Catalog, RequestTemplate, FormSchema, сценарный runtime и механизм политик Helpdesk сохраняются.

Прототип является **визуальным и функциональным ориентиром**, а не эталоном серверной архитектуры. Его локальные вычисления SLA, маршрутизации и приоритета нельзя переносить в production как отдельную бизнес-логику.

Перед реализацией проверить актуальный `main`, состояние миграций и действующие контракты. Если они изменились после указанного SHA, адаптировать ТЗ к фактическому состоянию кода, сохранив функциональные требования.

# 2. Итоговая структура интерфейса

В Guided Request Studio оставить **три основных раздела**:

| Раздел | Назначение |
|---|---|
| **Каталог** | Создание карт сценариев, управление категориями, обзор точек входа и поиск |
| **Карта сценария** | Полный визуальный редактор: блоки, связи, точки входа, вопросы, политики, обработка, тестирование |
| **Согласования** | Создание и использование схем согласования заявок руководителями |

Удалить из основной навигации отдельные разделы:

- «Пункты и входы»
- «Настройки элементов»
- «Обработка»
- «Тестирование»
- «Публикация»

Их функциональность не удаляется, а переносится в контекстные инспекторы, панели и действия карты.

Тестирование и публикация остаются доступными через кнопки в заголовке редактора. История и версии — через компактный элемент управления версиями.

Не создавать отдельные страницы для параметров, которые можно удобно настроить в инспекторе выбранного блока.

## 2.1. Каталог

В административном каталоге основной объект — **карта сценария**.

Пример:

**Рабочее место → Принтеры → Проблемы с печатью**

Карточка карты показывает название, описание, количество опубликованных точек входа, статус черновика, активную версию и дату изменения.

Внутри карты могут быть точки входа:

- Не печатает.
- Застряла бумага.
- Бледная печать.
- Ошибка на принтере.

Точки входа не создают независимые копии сценария.

Каталог администратора позволяет создавать новые карты, выбирать категории, искать сценарии и открывать редактор. Управление конкретной точкой входа осуществляется прямо на карте сценария.

При этом действующая модель Service/Offering сохраняется. Новая административная визуализация не создаёт второй независимый каталог услуг.

## 2.2. Карта сценария

Основной экран — полноразмерный визуальный граф.

Рабочие области:

**Слева:** компактная библиотека блоков, список точек входа текущей карты, поиск элементов.

**В центре:** редактируемый граф с масштабированием, панорамированием, перетаскиванием блоков и изменением соединений.

**Справа:** контекстный инспектор выбранного блока или связи.

Сотруднический предпросмотр открывается из карты в боковой панели. На широком экране допускается закрепление предпросмотра рядом с инспектором, если остаётся достаточно места для графа.

Инспектор не должен перекрывать граф плавающим окном без необходимости.

Выбор пустой области показывает общую информацию о сценарии. Выбор блока — его настройки. Выбор стрелки — правила перехода.

Основная работа должна выполняться без постоянных переходов между экранами.

# 3. Блок «Начало»

Добавить на каждую карту системный элемент **«Начало»**.

Он существует в единственном экземпляре и не может быть удалён администратором.

Его назначение — общие настройки карты.

### Основные настройки

- Название сценария.
- Описание.
- Категория и расположение в каталоге.
- Привязка к существующей Service/Offering.
- Связанный RequestTemplate.
- Базовые политики обработки и наследование.
- Статус карты и обзор точек входа.

### Расширенные настройки

- Стабильные идентификаторы и технические ключи.
- Дополнительные параметры контекста.
- Технические зависимости.
- Сведения о версиях и совместимости.

**Важно:** «Начало» — визуальный системный элемент метаданных карты, а не обязательный исполняемый узел сценарного runtime.

Несколько точек входа могут начинаться с разных реальных блоков. Все маршруты не обязаны проходить через единственный исполняемый Start.

Для существующих сценариев с одним `entry_block_id` обеспечить совместимое поведение.

# 4. Типы блоков

Использовать семь основных пользовательских типов блоков.

| Блок | Назначение | Соответствие существующему runtime |
|---|---|---|
| **Вопрос** | Сбор одного или нескольких ответов | `form_page` |
| **Инструкция** | Показ инструкции и справочной информации | `instruction` |
| **Условие** | Выбор дальнейшей ветки | `decision` |
| **Проверка результата** | Подтверждение, помогли ли действия | `resolution_check` |
| **Диагностика** | Получение диагностического результата | `diagnostic` |
| **Сводка** | Проверка введённых данных перед отправкой | `review` |
| **Результат** | Завершение без обращения или создание заявки | `finish` / `submit_ticket` |

Дополнительный системный элемент «Начало» не включать в палитру создаваемых блоков.

Семь визуальных типов покрывают существующие восемь исполняемых типов. Не нужно создавать новый серверный исполнитель для каждого нового визуального оформления.

## 4.1. Блок «Вопрос»

Администратор задаёт вопрос, выбирает тип ответа и его варианты.

Использовать существующие поддерживаемые типы полей: текст, список, множественный выбор, число, дата, пользователь, подразделение, устройство и другие доступные в актуальном контракте.

Один блок может содержать несколько вопросов.

Настройки вопроса:

- Название и текст.
- Тип ответа.
- Обязательность.
- Варианты ответа.
- Подсказка.
- Разрешение ответа «Не знаю».
- Условия видимости.
- Проверка корректности значения.

### Влияние ответа на обработку

Добавить простой выбор назначения ответа:

- Диагностический вход.
- Масштаб воздействия.
- Срочность.
- Важность.
- Маршрутизация.
- Данные согласования.
- Отчётность.
- Контекст обращения.

Разрешить несколько совместимых назначений для одного поля.

Это должно сопоставляться с существующими `process_mapping.roles`, а не с новой параллельной системой.

Не создавать самостоятельные блоки «Масштаб», «Срочность» и «SLA».

Пример:

Вопрос «Кто не может печатать?» → роль `priority_impact`.

Вопрос «Можете продолжать работу?» → роль `priority_urgency`.

Ответы передаются существующему механизму политик, который вычисляет приоритет и сроки.

### Расширенные настройки

Внутри выбранного вопроса раскрываются стабильный ключ, fact key, зависимости, дополнительные условия, технические ограничения и совместимые роли.

Не использовать отдельную общую вкладку расширенных настроек.

## 4.2. Инструкция

Поддерживать безопасное форматирование, текст, подсказки и подтверждение ознакомления.

Инструкцию можно использовать в общих и специализированных ветках.

Не добавлять возможность выполнять произвольный HTML или JavaScript.

## 4.3. Условие

Условие связывает входные факты, ответы и допустимые результаты предыдущих шагов.

Основные операции на человеческом языке:

- Равно.
- Не равно.
- Содержит один из вариантов.
- Больше/меньше.
- Значение существует.
- И / ИЛИ / НЕ.

Условия должны использовать существующий типизированный DSL сценариев.

Для простого выбора варианта ответа условие можно задавать непосредственно на стрелке исходящего перехода. Отдельный блок «Условие» нужен для более сложных комбинаций.

Не создавать два разных движка условий.

## 4.4. Проверка результата

Блок задаёт пользователю вопрос, помогло ли предложенное решение.

Результаты:

- Да.
- Нет.
- Не знаю.

Положительный ответ может привести к самостоятельному завершению.

Отрицательный или неизвестный результат — к дальнейшей диагностике либо созданию обращения.

Сохранить действующее серверное правило: завершение как самостоятельное решение допустимо только после явной положительной проверки результата.

## 4.5. Диагностика

Блок предназначен для будущей интеграции с Endpoint.

На текущем этапе сохранить честное состояние фактических возможностей. Если выполнение диагностики до обращения недоступно, показывать «Недоступно» и переходить по предусмотренному безопасному маршруту.

Не имитировать успешное выполнение реальной диагностики.

Будущие операции требуют поддерживаемой capability, разрешений и проверки согласия там, где оно необходимо.

## 4.6. Сводка

Показать сотруднику собранные ответы перед отправкой обращения.

Позволить вернуться и исправить данные.

Не раскрывать внутренние идентификаторы политик, очередей или технические сведения, недоступные заявителю.

## 4.7. Универсальный блок «Результат»

В визуальной палитре оставить **один тип «Результат»** с двумя режимами.

### Режим А — Завершить без обращения

- Настроить итоговое сообщение.
- Показать рекомендации.
- Завершить прохождение без создания заявки.
- Обязательно сохранить серверную проверку положительного подтверждения решения.

### Режим Б — Создать обращение

- Показать связанный тип обращения и RequestTemplate.
- Показать эффективные политики обработки.
- Показать рассчитанные очередь, приоритет и SLA в режиме предпросмотра.
- Показать необходимость согласования.
- Дать сотруднику проверить данные и подтвердить отправку.
- Создать обращение исключительно через существующий серверный API Helpdesk.

Для администратора это один визуальный тип, но на уровне runtime используются действующие `finish` и `submit_ticket`.

Допускается несколько завершающих блоков на одной карте.

**Ограничение:** сегодня политика обработки привязана к сценарию и каноническому контексту услуги/шаблона. Нельзя представлять каждый завершающий блок как самостоятельный источник политики, если такого контракта на сервере нет.

По умолчанию все завершающие блоки одного сценария используют общий канонический контекст. Различия приоритета, сроков и маршрута определяются действующими политиками по собранным данным.

Если требуется принципиально иной тип обращения или Offering, использовать отдельную каноническую привязку либо явно расширенный проверяемый серверный контракт. Не переключать Offering простым пользовательским параметром.

# 5. Полноценное редактирование графа

Это обязательная функциональность, а не декоративная возможность.

## 5.1. Перемещение блоков

Блок можно перетаскивать по холсту.

Изменение положения **не изменяет логику переходов**.

Позиции необходимо сохранять между открытиями редактора.

Координаты относятся к метаданным визуального редактора и не должны нарушать строгую схему исполняемого сценария.

## 5.2. Соединение блоков

У блока есть визуальные точки подключения.

Администратор может перетянуть исходящую связь на другой допустимый блок.

При переподключении изменяется только выбранный маршрут.

Другие связи и условия остаются без изменений.

При выборе стрелки справа открывается инспектор:

- Название/условие перехода.
- Значение ответа или результата.
- Целевой блок.
- Приоритет сопоставления при необходимости.
- Резервный маршрут.

Изменения сохраняются как редактирование канонических `transitions`.

## 5.3. Добавление блока на существующую стрелку

Если администратор переносит новый блок непосредственно на существующую связь, предложить действие «Вставить между шагами».

Система создаёт:

`Исходный блок → Новый блок → Прежний целевой блок`.

Исходное условие перехода сохраняется на первом соединении. Второе соединение становится обычным продолжением, если это допустимо для типа нового блока.

Если вставляется конечный блок или возникает несовместимая логика, не выполнять автоматическое переподключение.

## 5.4. Удаление блока

При удалении необходимо проверять:

- Входящие связи.
- Исходящие связи.
- Привязанные точки входа каталога.
- Зависимости условий.
- Использование полей другими блоками.

Если блок используется точкой входа, предложить назначить другой допустимый блок или убрать соответствующую точку входа из черновика.

Не перенаправлять её молча на соседний элемент.

Изменение, которое затрагивает несколько связей или точек входа, должно выполняться как одна атомарная операция редактора с возможностью отмены.

## 5.5. Дополнительные операции

Поддержать копирование блока, Undo/Redo, масштабирование, панорамирование, подгонку карты под экран, поиск блока и подсветку ошибок.

Копирование должно создавать новые стабильные идентификаторы и корректно переносить допустимые локальные зависимости.

Серверный runtime сейчас запрещает автоматические циклы в графе. Сохранить это ограничение. Не разрешать визуально соединения, которые создают запрещённый цикл, выдавая понятное объяснение.

Возврат сотрудника к предыдущему вопросу выполняется существующим механизмом навигации сеанса, а не бесконечным циклом исполнения.

# 6. Точки входа непосредственно на карте

Отдельную страницу «Пункты и входы» убрать.

У выбранного обычного блока добавить действие:

**«Добавить точку входа из каталога»**.

После выбора в том же инспекторе появляются:

- Название пункта.
- Краткое описание.
- Категория каталога.
- Синонимы и поисковые фразы.
- Доступность.
- Начальный блок.
- Сообщённый симптом / исходный контекст.

Один блок может иметь несколько точек входа.

Точки входа отображаются на карте небольшими маркерами, позволяющими быстро выбрать и изменить привязку.

Название пункта редактируется здесь же. Отдельная страница для этого не требуется.

Категории можно создавать через компактный вложенный редактор, не теряя несохранённое состояние карты.

## 6.1. Пример

Карта «Проблемы с печатью»:

- «Не печатает» → общий вопрос о симптомах.
- «Застряла бумага» → безопасная инструкция устранения замятия.
- «Бледная печать» → проверка качества печати.
- «Ошибка на принтере» → уточнение кода ошибки.

После специализированных шагов маршруты могут объединяться в общие блоки диагностики, оценки масштаба, срочности и проверки результата.

Никаких копий общих блоков или полных сценариев под каждый пункт каталога.

## 6.2. Контекст точки входа

Введённый сотрудником симптом и выбор пункта каталога считать сообщённой информацией, а не подтверждённым диагностическим фактом.

Разделять:

- `reportedSymptom` — что сообщил сотрудник.
- `answers` — ответы сотрудника.
- `verifiedFacts` — сведения, действительно подтверждённые доверенными источниками или проверками.

Не повышать автоматически степень доверия к данным из каталога.

Специализированная точка входа не должна обходить обязательные вопросы или проверки, необходимые для формирования корректного обращения.

## 6.3. Публикация точек входа

Точка входа должна ссылаться на конкретную опубликованную версию сценария и допустимый блок внутри неё.

При публикации новой версии графа одновременно публиковать согласованный набор его точек входа.

Не допускать ситуации, когда пункт каталога уже ссылается на новую структуру, а пользовательский сеанс продолжает ожидать старые связи.

Новые сеансы используют новую версию; уже начатые закреплены за прежней.

Сохранять эффективные ограничения видимости Service, Offering и иерархии категорий.

# 7. Обработка, приоритеты и SLA — внутри карты

Отдельную вкладку «Обработка» удалить.

Её функциональность распределить по следующим элементам.

### «Начало»

- Базовая привязка к услуге.
- RequestTemplate.
- Политики по умолчанию.
- Наследование параметров обработки.

### «Вопрос»

- Роль ответа.
- Масштаб воздействия.
- Срочность.
- Важность.
- Данные для маршрутизации и согласования.

### «Результат → Создать обращение»

- Эффективная очередь.
- Рассчитанный приоритет.
- SLA первой реакции.
- SLA решения.
- Применяемая политика согласования.
- Основания вычисленного результата в режиме администратора.

**Не реализовывать отдельный вычислитель SLA, приоритета или маршрутизации внутри Studio.**

Источник результата — существующий серверный policy runtime.

При изменении ответа в тестовом предпросмотре пересчитывать ожидаемые параметры через действующий безопасный серверный preview/simulation, а не локальную копию правил.

Если определённая политика не может быть применена, показывать источник ошибки. При публикации блокировать действительно недопустимую конфигурацию.

Не путать «сотрудник сообщил, что весь отдел не работает» с подтверждённой неисправностью оборудования всего отдела. Действующая политика вправе учитывать такой ответ как входные данные, но интерфейс обязан правильно показывать источник сведений.

# 8. Раздел «Согласования»

Третья основная вкладка предназначена **именно для согласования обращений руководителями**, а не согласования публикации сценариев администраторами.

Раздел представляет собой удобный интерфейс управления существующими политиками согласований Helpdesk.

Поддержать предусмотренные сервером режимы:

- Достаточно одного согласующего.
- Требуется согласие всех.
- Последовательное согласование.

Источники согласующих, если поддерживаются действующим сервером: непосредственный руководитель заявителя, владелец услуги, руководитель очереди, определённая группа или явно назначенные согласующие.

Не создавать отдельный механизм согласований.

### Пример

Сценарий выявляет необходимость замены неисправного устройства.

При создании обращения действующая политика может требовать согласования руководителем подразделения.

Согласование выполняется после создания обращения через существующий механизм заявок и статусов.

Диагностический граф не должен становиться вторым асинхронным движком согласований.

В инспекторе блока «Результат» администратор видит применяемую схему согласования и может выбрать опубликованную политику в рамках существующих серверных ограничений.

При определении руководителя использовать доверенный серверный контекст. Нельзя принимать произвольно переданный клиентом идентификатор руководителя как авторитетный источник полномочий.

Если обязательного согласующего невозможно определить, соблюдать действующее безопасное поведение серверной политики. Не назначать случайного пользователя.

# 9. Тестирование внутри карты

Добавить кнопку **«Тестировать»** в заголовке.

Она открывает интерактивную панель, не меняя основную навигацию.

Администратор выбирает точку входа и проходит сценарий как сотрудник.

В процессе:

- Подсвечивается текущий блок.
- Отображается пройденный путь.
- Показываются ответы и результаты условий.
- Разделяются сообщённые и проверенные факты.
- На этапе создания обращения показываются рассчитанные политики.
- Ошибки позволяют перейти непосредственно к проблемному блоку или стрелке.

Предусмотреть проверку всех допустимых входов, включая специализированные.

Не создавать реальные заявки, диагностические операции, согласования или уведомления во время симуляции.

Поддерживать безопасные результаты недоступной диагностики, включая отказ, тайм-аут и отсутствие capability.

Режим тестирования должен использовать те же серверные правила переходов и обработки, что и рабочее прохождение.

Если черновик содержит ошибки, позволить тестировать допустимую часть, но явно показывать ограничение. Недопустимую карту нельзя публиковать.

# 10. Публикация и версии

Кнопка **«Опубликовать»** открывает панель публикации.

Проверить:

- Структуру графа.
- Доступность и корректность всех точек входа.
- Корректность переходов.
- Отсутствие недостижимых обязательных участков.
- Наличие допустимых завершений.
- Обязательные поля на каждом маршруте к созданию заявки.
- Политики и канонические привязки.
- Результаты серверной проверки готовности.

Показать изменения относительно действующей версии.

При обнаружении ошибки добавить действие «Перейти к блоку» или «Перейти к связи».

Публиковать только после явного подтверждения администратора.

Сохранять действующие права, аудит, неизменяемость версий и серверную защиту публикации.

Черновик может содержать неполную схему. Опубликованная версия — нет.

Автосохранение черновика должно отображать статус и ошибки. Сохранение не равно публикации.

История версий доступна через заголовок карты.

Восстановление предыдущей версии создаёт новый черновик, не переписывая старые опубликованные версии.

# 11. Архитектурные изменения backend

Это расширение существующей модели, а не создание нового workflow engine.

Текущая каноническая цепочка:

`Service → Offering → RequestTemplate/FormSchema → Policy Runtime → Ticket`.

Guided Request Studio использует эту цепочку.

## 11.1. Новая модель нескольких входов

Добавить серверную поддержку связи:

`CatalogItem → EntryPoint → ScenarioVersion + TargetBlock`.

Для каждого пункта каталога должны храниться стабильная идентичность, категория, заголовок, описание, поисковые синонимы, ограничения доступности и целевой блок соответствующей версии.

Выбрать минимальную additive-модель хранения, совместимую с действующими сценарными таблицами.

Не создавать отдельный Service или Offering для каждого симптома.

Не удалять существующую связь сценария с Offering без обоснованной необходимости.

Существующие сценарии с единственным `entry_block_id` должны продолжать работать через совместимый маршрут.

## 11.2. Контракты и исполнение

Расширить DTO/API и серверный runtime таким образом, чтобы выбранная точка входа:

1. Проверялась на доступность и права.
2. Разрешалась в опубликованную версию.
3. Определяла допустимый начальный исполняемый блок.
4. Закреплялась за создаваемым пользовательским сеансом.
5. Не могла быть произвольно подменена клиентом после создания сеанса.

Версии графа и набор привязанных входов публиковать согласованно и атомарно.

При публикации проверять все входы. Проверки обязательных данных, достижимости, условий, положительного завершения и источников политики должны учитывать специализированные маршруты.

Учитывать существующие ограничения определения сценария, размера входных данных, числа блоков и лимита проверки вариантов. При превышении серверных ограничений корректно блокировать публикацию с объяснением, а не отключать проверки.

Не менять систему авторизации и полномочий для обхода этих ограничений.

## 11.3. Совместимость

Сохранить работу:

- Существующих опубликованных сценариев.
- Обычных форм без сценариев.
- Service Catalog.
- Существующих RequestTemplate и FormSchema.
- Политик и правил обработки.
- Активных пользовательских сеансов.
- API Endpoint и существующих контрактов Helpdesk.

Миграции должны быть добавочными. Использовать фактическую текущую ревизию Alembic, не предполагать номер следующей миграции заранее.

Не переписывать исторические заявки и опубликованные версии.

## 11.4. Поведение ошибочных изменений

Обязательные правила:

| Операция | Поведение |
|---|---|
| Перемещение блока | Меняет только расположение |
| Переподключение стрелки | Меняет только выбранный переход |
| Вставка блока на стрелку | Переподключает этот маршрут, сохраняя условие |
| Удаление блока с точкой входа | Требует переназначения или удаления привязки в черновике |
| Удаление используемого поля | Показывает зависимости и не оставляет скрытые повреждённые ссылки |
| Добавление недопустимого цикла | Запрещается с объяснением |
| Переход к завершению без обязательных данных | Блокируется при проверке готовности |
| Завершение без положительной проверки | Блокируется существующей серверной валидацией |
| Изменение опубликованной карты | Создаёт черновик новой версии |
| Продолжение старого пользовательского сеанса | Использует закреплённую версию |

Любая многошаговая операция редактирования графа должна быть атомарной для состояния редактора.

# 12. Дизайн и удобство использования

Сохранять существующий визуальный язык Helpdesk и выбранное направление Product Design Studio v3.

Основные требования:

- Крупный читаемый граф.
- Компактная библиотека блоков.
- Контекстный инспектор справа.
- Минимальное количество вкладок и промежуточных экранов.
- Понятные названия элементов без обязательного знания внутренних DTO.
- Расширенные настройки внутри конкретного выбранного элемента.
- Простая настройка точки входа прямо на блоке.
- Предпросмотр пользователя без выхода из редактора.
- Поддержка клавиатуры, понятных фокусов и доступных альтернатив drag-and-drop.
- Рабочая компоновка на стандартных десктопных разрешениях.
- Видимые состояния загрузки, сохранения, конфликта версий и ошибок.

Не добавлять отдельные экраны, если их функции могут быть реализованы через существующий инспектор или контекстную панель.

Не заставлять администратора вручную создавать технический шаблон, Offering и сценарий как несколько независимых процессов, когда их можно безопасно связать существующим мастер-процессом создания карты.

# 13. Последовательность реализации

Выполнить задачу в одной функциональной ветке, без искусственных остановок между согласованными частями.

### Шаг 1. Адаптация к текущему Helpdesk

Изучить действующие компоненты Guided Request Studio, Service Catalog, политики, runtime, миграции и frontend.

Зафиксировать необходимые изменения существующих контрактов.

Не проводить отдельный большой архитектурный аудит. Нужна только достаточная проверка применимости целевой модели.

### Шаг 2. Поддержка нескольких точек входа

Реализовать модель хранения, DTO/API, выполнение, версионирование, публикацию и проверки готовности для нескольких точек входа.

Сохранить совместимость со старым `entry_block_id`.

Добавить целевые серверные тесты.

### Шаг 3. Новый визуальный редактор

Использовать существующий прототип как визуальный ориентир.

Перенести необходимую функциональность в текущий React frontend:

- Три раздела.
- Системное «Начало».
- Библиотека блоков.
- Контекстный инспектор.
- Редактируемые стрелки.
- Добавление блоков на связи.
- Точки входа внутри инспектора.
- Семантически единый визуальный блок «Результат».
- Undo/Redo и сохранение геометрии.

Не переносить демонстрационные вычислители политик из прототипа.

### Шаг 4. Настройки и обработка

Перенести настройки вопросов, условий, назначения ролей, маршрутизации, приоритетов, SLA и согласований непосредственно в карту.

Подключить существующий policy runtime.

Создать удобный интерфейс схем согласования руководителями, переиспользующий действующий backend.

### Шаг 5. Пользовательский каталог и прохождение

Обеспечить публикацию пунктов каталога и запуск сценария из разных точек входа.

Сохранить существующие формы и fallback-механизмы.

Обеспечить корректное закрепление версии за сеансом и отправку обращения через канонический API.

### Шаг 6. Интеграционная проверка

Проверить сквозной сценарий, применимые backend/frontend тесты, сборку и работу основных пользовательских маршрутов.

Запустить существующие обязательные CI-проверки в соответствии с принятым процессом репозитория.

Не добавлять независимо от реального риска множество повторных ревью, формальных GO/NO-GO, дублирующих CI-прогонов и объёмных evidence-отчётов.

Codex может самостоятельно исправлять ошибки и завершать согласованную задачу.

# 14. Приёмочные сценарии

## Сценарий 1. Несколько точек входа

Администратор создаёт карту «Проблемы с печатью».

Добавляет три пункта каталога:

- Не печатает.
- Застряла бумага.
- Бледная печать.

Каждый пункт может начинаться с выбранного допустимого блока.

Общая диагностика не дублируется.

## Сценарий 2. Редактирование графа

Администратор перетаскивает блок, меняет соединение и вставляет новый вопрос между существующими шагами.

Новая схема правильно сохраняется и воспроизводится.

Положение блока не меняет маршрут само по себе.

## Сценарий 3. Удаление начального блока

Администратор пытается удалить блок, на который указывает опубликованный пункт каталога.

Редактор показывает зависимость и требует осознанного решения в черновике.

Нельзя незаметно сломать пользовательский вход.

## Сценарий 4. Масштаб, срочность и SLA

Сотрудник сообщает, что не может печатать весь отдел и работа остановлена.

Вопросы сохраняют ответы с корректными ролями.

Серверные политики вычисляют соответствующий приоритет, сроки и маршрут.

Не используется локальный самодельный SLA-движок.

## Сценарий 5. Самостоятельное решение

Сотрудник проходит инструкцию и явно подтверждает решение проблемы.

Сценарий завершается без заявки.

## Сценарий 6. Создание обращения

Сотрудник не смог решить проблему.

Показывается сводка, затем сотрудник подтверждает создание обращения.

Обращение создаётся с действующими серверными политиками.

## Сценарий 7. Согласование руководителем

Для обращения, требующего согласования, применяется опубликованная схема.

Руководитель определяется доверенным серверным механизмом.

Согласование проходит через существующий жизненный цикл заявки.

## Сценарий 8. Изменение опубликованной версии

Администратор меняет граф и одну точку входа.

Новая версия публикуется согласованно.

Старые активные сеансы продолжают использовать прежнюю версию.

## Сценарий 9. Проверка безопасности маршрутов

Специализированная точка входа не позволяет обойти обязательные данные, необходимые для создания обращения.

Повреждённые связи, запрещённые циклы, недоступные политики и незавершённые маршруты дают понятную ошибку и блокируют публикацию.

## Сценарий 10. Существующие сценарии

Ранее опубликованные сценарии с единственной точкой входа и обычные формы продолжают работать без обязательной ручной миграции каждого сценария.

# 15. Ожидаемый итог

После завершения разработки администратор должен иметь возможность:

1. Открыть каталог и создать карту «Проблемы с печатью».
2. Настроить общие параметры через «Начало».
3. Создать вопросы, инструкции и проверки непосредственно на графе.
4. Настроить связи перетаскиванием стрелок.
5. Назначить нескольким блокам точки входа из каталога.
6. Добавить синонимы для поиска прямо в инспекторе.
7. Настроить влияние ответов на существующие политики приоритета и SLA.
8. Настроить использование действующих согласований руководителем.
9. Проверить сценарий с разных точек входа.
10. Опубликовать версию и увидеть соответствующие пункты в каталоге сотрудника.

**Ключевой критерий успешности:** для выполнения этих действий администратору не требуется переключаться между множеством независимых редакторов сущностей и вручную поддерживать их согласованность.

## Требования к завершению работы Codex

- Реализовать функциональность в основном Helpdesk, а не только в отдельном прототипе.
- Не изменять production-сервисы и не публиковать реальные сценарии автоматически.
- Не ослаблять существующие серверные гарантии безопасности, авторизации, публикации и проверки политик.
- Выполнить необходимые целевые тесты и применимые проверки интеграции.
- Подготовить изменения в функциональной ветке для принятого в репозитории процесса объединения.
- Предоставить краткую сводку реализованного, изменений контрактов, результатов тестирования и оставшихся реальных ограничений.

**Итоговая архитектурная цель:**

Одна карта сценария → множество точек входа → общая диагностика → собранные структурированные данные → существующие политики Helpdesk → решение без обращения либо создание и обработка заявки.

Без дублирования сценариев, второго SLA-движка и лишних административных экранов.
