## Дополнение: PostgreSQL и ревью тестов

Настроен локальный PostgreSQL16.15 из официального EDB binary ZIP. Сверенный
SHA256: `43bb45f173a6f08cf1d29a97a6d8deb119e8e8093a24c00d2d1001a0ccaa8281`.
Повторяемый запуск: `scripts/run_with_local_postgres.py`; порядок подготовки и
команда описаны в [правилах тестирования](TESTING_RULES.md).

Для каждого запуска создаётся отдельный кластер с SCRAM, случайным паролем и
loopback-портом. Существующие внешние настройки БД не используются. Хранилище
и бинарники находятся в игнорируемой `.run`; пароль не сохраняется в репозитории.
Кластер автоматически останавливается и удаляется после тестов.

Ревью тестов выявило и устранило:

- Неполную очистку UI-токенов: файл role-тестов переведён на профиль `full`,
  каждый параметр проверяет пустую таблицу сессий.
- Ложное доказательство конкуренции через 200мс ожидания: теперь независимое
  соединение проверяет реальный blocker PID в `pg_blocking_pids`.
- Отсутствие PostgreSQL-сценария обратного порядка массового назначения:
  добавлены конкурентные запросы и подтверждение блокировки до захвата нагрузки.
- Слабую проверку смены роли: настоящий токен проходит production middleware
  и административный HTTP-обработчик с ответами200/403/401, проверяются обе
  отозванные сессии в БД.

  production-файлы для проверки не изменялись.

## Дополнение: полный CI перед публикацией

Канонический `scripts/run_ci_suite.py` запущен через изолированный PostgreSQL
runner. Для проверки до пользовательского коммита создан отдельный локальный
Git-снимок внутри игнорируемой `.run`: сборка требует чистых committed frontend
inputs. Временные снимки не публикуются; итоговый HEAD проверяется повторно
перед обычным push.

Полный запуск выявил дополнительные дефекты тестовой инфраструктуры:

- Вывод pnpm приводил к UnicodeEncodeError при перенаправлении в старую Windows
  кодировку. Внешний CLI явно использует UTF-8; добавлены ASCII/CP1251 регрессии.
- В браузерном тесте URL второго тикета появлялся до commit интерфейса. Тест
  начинал ввод в старый composer, после чего штатный сброс стирал текст.
  Переход теперь ждёт успешный workspace-ответ и заголовок нужного тикета.
  Проверка без retry: 40/40 повторов двух сценариев на двух разрешениях.
- Windows PostgreSQL выполняет checkpoint при DROP DATABASE для освобождения
  файловых дескрипторов фоновых процессов. Измерено ожидание IPC/CheckpointDone
  без блокирующих транзакций. Только Windows DROP получает ограниченный бюджет
  SQL90/операции95 секунд; обычные SQL30/операции35/блокировки5 не изменены.
- Один checkpoint полного прогона занял176 секунд (103 — синхронизация файлов).
  Только для нового одноразового кластера wrapper задаёт fsync/full_page_writes/
  synchronous_commit=off. Это ускоряет проверки схемы/бизнес-правил/блокировок;
  сохранность при аварии питания не проверяется. Такой режим описан в
  [PostgreSQL16](https://www.postgresql.org/docs/16/non-durability.html).
- Traceback ошибки cleanup сохранял пароль одноразовой БД в логе слоя и JUnit.
  Скрытие credentials перенесено перед записью вывода; отчёты и summary также
  очищаются. Для прерванных шагов сначала завершается дочерний процесс.

Промышленная БД, staging и установленные службы не изменялись.
