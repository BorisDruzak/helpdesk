# VNC-подключение с сервера к агенту — анализ

**Цель:** возможность с сервера (веб-панели) подключаться к удалённому рабочему столу агента через VNC.

**Дата:** 2026-03-04

---

## 1. Текущая архитектура (кратко)

- **Агент** подключается к **серверу** по WebSocket (исходящее соединение). Сервер не открывает TCP к агенту.
- Агент может быть за NAT/файрволом; единственный стабильный канал — WebSocket агент → сервер.
- Уже есть: модуль **screen** (скриншоты, запись в MP4), локальный **UiApiServer** на агенте (127.0.0.1:8765), Protocol V3, аутентификация по токену.

---

## 2. Что нужно для VNC «сервер → агент»

### 2.1 Ограничение

Сервер **не может** сам открыть TCP-соединение к агенту (агент за NAT, инициатор — агент). Поэтому «VNC с сервера к агенту» реализуется только так:

1. На **агенте** поднимается VNC-сервер (или источник картинки экрана).
2. Трафик к этому серверу доставляется **через уже существующий исходящий канал** (WebSocket агент → сервер), т.е. туннель/прокси поверх WS.
3. **Сервер** принимает подключения от браузера (или от VNC-клиента) и проксирует поток к агенту по этому туннелю.

Итого: нужен **reverse-туннель** (агент «выносит» свой VNC-порт на сервер) или **проксирование VNC-протокола поверх WebSocket**.

---

## 3. Варианты реализации

### Вариант A: noVNC + websockify поверх WebSocket (рекомендуемый подход)

**Идея:** на агенте — классический VNC-сервер (x11vnc, TigerVNC и т.п.) + **websockify** (обёртка «TCP VNC → WebSocket»). Агент открывает **отдельное** WebSocket-соединение к серверу специально для VNC и гонит по нему кадры/события VNC. Сервер принимает этот WS и отдаёт его noVNC-клиенту в браузере.

**Схема:**

```
[Браузер] ←→ noVNC (JS) ←→ [Сервер: WS endpoint /vnc/{device_id}] ←→ [WS] ←→ [Агент: websockify → VNC server]
```

**На агенте:**

- Установка и запуск VNC-сервера (например x11vnc для Linux, TigerVNC для Windows).
- Процесс/модуль **websockify**: слушает `localhost:5900` (VNC), поднимает исходящий WebSocket к серверу (например `wss://server/vnc-tunnel?device_id=...&token=...`) и проксирует туда VNC-трафик (binary frames).
- Управление жизненным циклом: запуск VNC-сессии по команде с сервера (например через `run_tool` или отдельную команду протокола), остановка по таймауту или явному запросу.

**На сервере:**

- Маршрут `GET /vnc/{device_id}` (или отдельный поддомен) — отдаёт HTML+JS noVNC.
- WebSocket endpoint `wss://server/vnc-tunnel` (или `/ws/vnc`) для входящих соединений **от агента** (по токену + device_id). Сервер связывает `device_id` с этим WS.
- Когда пользователь открывает «VNC к устройству» в админке, браузер подключается к тому же endpoint как noVNC-клиент; сервер проксирует кадры между браузером и уже подключённым агентом по device_id (два WS: браузер ↔ сервер ↔ агент).

**Плюсы:** стандартный VNC, полное управление (мышь, клавиатура), не изобретаем протокол.  
**Минусы:** нужен VNC-сервер и websockify на агенте, поддержка платформ (Windows/Linux/macOS).

---

### Вариант B: Обратный TCP-туннель (generic port forward)

Агент поднимает локально VNC на `127.0.0.1:5900` и открывает к серверу **один долгоживущий WebSocket** «туннель». Сервер по этому WS проксирует один TCP-поток (например, свой слушающий порт 15900 → туннель → агент:5900). Браузер подключается к `server:15900` через noVNC+websockify на стороне сервера или отдельный TCP-клиент.

**Схема:**

```
[Браузер] ←→ noVNC → [Сервер: порт 15900] ←→ [WS tunnel] ←→ [Агент: localhost:5900 VNC]
```

**На агенте:** один туннельный процесс: читает из локального сокета (VNC), пишет в WebSocket; читает из WebSocket, пишет в локальный сокет.  
**На сервере:** для каждого device_id — один слушающий порт (или один порт с мультиплексированием по device_id в начале потока). Сложнее масштабировать и безопасно изолировать.

**Плюсы:** можно туннелить любой TCP (не только VNC).  
**Минусы:** управление портами на сервере, привязка к device, сложнее изоляция и масштабирование.

---

### Вариант C: «Живой» поток без VNC (MJPEG / WebRTC поверх WS)

Использовать уже существующий модуль **screen** (захват через mss): периодически делать скриншоты и отправлять кадры по WebSocket на сервер; сервер отдаёт MJPEG или другой поток в браузер. Управление (мышь/клавиатура) — отдельно (например, команды через run_tool или отдельный канал).

**Плюсы:** не нужен VNC-сервер на агенте, только Python + mss.  
**Минусы:** не «настоящий» VNC, задержка и нагрузка при высоком FPS, ввод с клавиатуры/мыши нужно проектировать отдельно.

## 4. Что пригодится из текущего кода и инфраструктуры

| Компонент | Использование |
|-----------|----------------|
| **Protocol V3, WebSocket агент↔сервер** | Либо расширить протокол новым типом канала (vnc_tunnel), либо поднять отдельный WS только для VNC (проще изоляция и безопасность). |
| **Аутентификация (agent token, device_id)** | Новый WS для туннеля должен проверять токен и привязывать соединение к device_id (как в основном WS). Не доверять device_id из query/body — брать из токена (см. SECURITY_AND_AUTH.md). |
| **Модуль screen** | Вариант C: переиспользовать захват экрана; для A/B — не обязателен, но может пригодиться для «предпросмотра» до запуска VNC. |
| **run_tool / outbox** | Запуск и остановка VNC-сессии на агенте: отдельный инструмент (например `vnc.start_session`, `vnc.stop_session`) или системная команда через существующий модуль. |
| **Роли и consent** | Доступ к VNC только для определённых ролей (например support/admin), при необходимости — подтверждение пользователя на агенте (consent). |
| **Документация** | PROTOCOL_V3.md, SECURITY_AND_AUTH.md — описать новый endpoint и правила доступа; при необходимости ARTIFACTS_API или отдельный документ для «сессий удалённого доступа». |

## 5. Рекомендуемый порядок работ (вариант A)

1. **Спецификация и безопасность**
   - Описать контракт: как агент регистрирует VNC-канал (WS URL, query-параметры, заголовки), как сервер сопоставляет device_id и сессию.
   - Решить: один общий WS endpoint с параметром `?type=vnc_tunnel` или отдельный путь `/ws/vnc`.
   - Ограничение доступа: только определённые роли, при необходимости consent на агенте (встроить в модуль/команду запуска VNC).

2. **Агент**
   - Модуль или отдельный сервис: проверка наличия VNC-сервера (x11vnc/TigerVNC), при необходимости — инструкции/скрипты установки.
   - Запуск websockify (или аналог на Python): подключается к серверу по WS (с тем же токеном или отдельным «vnc token»), проксирует localhost:5900 ↔ WS.
   - Управление: команда/run_tool для старта/остановки VNC-сессии (и websockify), таймаут неактивности, логирование.

3. **Сервер**
   - WebSocket endpoint для приёма туннеля от агента (по токену → device_id).
   - HTTP endpoint для браузера: отдача noVNC-страницы с подключением к `wss://server/...` для своего device_id (с учётом сессии пользователя и ролей).
   - Проксирование: связка «браузер WS» ↔ «агент WS» по device_id.

4. **Веб-интерфейс**
   - В карточке устройства/тикета кнопка «Удалённый рабочий стол (VNC)»: открывает noVNC в новой вкладке с нужным device_id и авторизацией.

5. **Документация**
   - Обновить PROTOCOL_V3.md или добавить отдельный документ (например `server/docs/VNC_TUNNEL.md`): схема, безопасность, коды ошибок.
   - В SECURITY_AND_AUTH.md — кто имеет право на VNC, как передаётся токен/сессия в noVNC.

## 6. Риски и ограничения

- **Платформы:** VNC-сервер на Windows (TigerVNC, TightVNC и т.д.) и Linux (x11vnc, TigerVNC) — разные пути установки; возможен headless без GUI — тогда только «виртуальный» VNC или вариант C.
- **Производительность:** VNC по WebSocket даёт двойное кодирование; для слабых каналов полезно ограничение разрешения/качества на стороне VNC-сервера или websockify.
- **Безопасность:** VNC-пароль не должен утекать в логи; туннель должен быть только поверх TLS (wss://) и с проверкой токена на сервере.
- **Масштабирование:** много одновременных VNC-сессий — нагрузка на сервер (память, CPU на проксировании); при росте можно вынести прокси в отдельный сервис.

---

## 7. Вывод

Реализация VNC «с сервера к агенту» возможна за счёт **обратного туннеля поверх WebSocket**: агент поднимает VNC и websockify и сам подключается к серверу, сервер проксирует поток в браузер (noVNC). В проекте уже есть всё необходимое для аутентификации, привязки к устройству и ролям; нужно добавить отдельный WS-канал для VNC, управление сессией на агенте (в т.ч. через run_tool) и страницу noVNC в веб-интерфейсе. Модуль screen и Protocol V3 пригодятся для интеграции и, при отказе от классического VNC, для варианта с «живым» просмотром экрана без VNC-сервера.
