# Пользователи и реестры

Администратор управляет человеком и его доступом в `/app/admin/users`.
`/app/admin/registry` содержит справочники и работу с устройствами.

## Назначение специалиста техподдержки

1. Найти человека по ФИО, контактам или логину. Если карточки нет — создать её.
2. В единой карточке открыть «Учётная запись»: выбрать связанный вход, связать
   существующий свободный логин или создать новый с паролем.
3. Выбрать роль «Сотрудник техподдержки» и активировать учётную запись.
4. В «Права и очереди» выбрать рабочую очередь по названию и при необходимости
   группы доступа. Очереди, предоставленные группами, показываются отдельно от
   прямого назначения: снятие прямого назначения не отменяет групповые права.
5. Указать причину и сохранить доступ. Ошибка оставляет введённые значения для
   исправления; успешное сохранение подтверждается сообщением.

Карточка человека и учётная запись остаются разными объектами хранения.
Создание профиля само по себе не даёт права входа и роль поддержки.
При нескольких связанных входах администратор выбирает конкретный логин.
Свободные учётные записи остаются доступны для привязки к нужному человеку.

Общие группы, справочник прав, аудит, восстановление пароля и настройки полей
профиля находятся в разделе «Пользователи». Дополнительные операции с человеком
сохраняют существующие проверки причин, предпросмотра и подтверждения.

В «Реестрах» остаются устройства, привязки и заявки на них, качество данных,
подразделения, помещения, аудитории и политики. Аудитории определяют видимость
материалов и сервисов, но не выдают роль и права сотрудника.
Старый `/app/admin/access` перенаправляет в настройки доступа «Пользователей».
Прямая ссылка на человека: `/app/admin/users?person=<person_id>`.

## Атомарный API учётной записи

Только администратор может читать и изменять
`/api/web/admin/users/{person_id}/account`.

- `GET`: success envelope, `data.accounts` — связанные учётные записи.
  `?user_login=<login>` позволяет прочитать назначения выбранного свободного
  логина перед привязкой, сохраняя существующие прямые очереди и группы.
  Учётная запись другого человека недоступна для перепривязки.
- `PUT`: `user_login`, необязательный `password`, `actor_role`, `is_active`,
  `queue_ids`, `group_ids`, обязательная `reason`;
  success envelope, `data.account` — сохранённое назначение.
- Проекция учётной записи: `user_login`, `actor_role`, `is_active`,
  `queue_ids`, `group_ids`. Идентификаторы очередей отражают прямые назначения.
- Изменение роли, подтверждённая связь с человеком, очереди, группы и аудит
  сохраняются одной транзакцией. Ошибки проверки не оставляют частичного доступа.
- Нельзя присвоить логин другого человека. Пароли и хеши не возвращаются и
  не включаются в аудит. Изменение не ослабляет серверные проверки доступа.
- Старые логины с разным регистром букв сохраняют одну запись назначения.
  Проверки членства понимают оба фактических варианта входа (пароль и SSO)
  только для однозначно определённой учётной записи; идентичность сессии и
  владельцы существующих заявок не меняются.

Миграция БД и изменения контрактов Endpoint Platform не требуются.
Браузерные fixture-тесты проверяют интерфейс на синтетических данных;
проверки PostgreSQL отдельно подтверждают сохранение и откат транзакций.
