# Тикетная система и обновление агента — текущее состояние и план доработок

**Дата:** 2026-03-15  
**Цель:** довести тикетную систему до рабочего идеала и вывести обновление агента в потоковом режиме с массовым обновлением по ОС.

---

## Часть 1. Тикетная система

### Желаемый порядок (из задачи)

1. Пользователь сталкивается с проблемой.
2. Создаёт заявку через агента или через веб.
3. Заявка прилетает на сервер (в админку).
4. Назначается вручную или автоматически суппорту.
5. Суппорт отрабатывает (статусы, взаимодействия с тикетом).
6. Суппорт выполняет заявку — **ожидает подтверждения от пользователя** и только тогда закрывает заявку.

### Что уже есть

| Этап | Реализация | Где |
|------|------------|-----|
| 1.1–1.2 | Создание заявки через агента (chat_raise) и через HTTP | `POST /api/tickets/create`, `websocket/agent_handler.py` (chat_raise → тикет в БД, status=new, requester_id=agent_id) |
| 1.3 | Заявка в БД и отображение в админке | Очередь тикетов в админке, карточка тикета, `ticket.js` |
| 1.4 | Назначение вручную и автоназначение | `POST /api/tickets/{id}/assign`, routing → очередь, assignment_service |
| 1.5 | Работа суппорта: статусы, сообщения, worklog, очередь | Workflow (statuses.py, workflow_service.py), POST message, Action Dock в ticket.js |
| 1.6 | Закрытие | Resolved → (автозакрытие через 72 ч или ручное Closed); requester может только reopen (Resolved → New) |

### Чего не хватает / где доработать

#### 1.6. Подтверждение пользователя перед закрытием

**Сейчас:** Суппорт переводит в «Решена» (resolved). Дальше либо автозакрытие через `TICKET_AUTO_CLOSE_HOURS` (72 ч), либо суппорт вручную переводит в «Закрыта». Явного шага «пользователь подтвердил — тогда закрыть» нет.

**Нужно:**
- Ввести явный сценарий: суппорт переводит в Resolved → пользователь (или агент от имени пользователя) подтверждает решение → тогда разрешать переход в Closed (или авто-закрытие по факту подтверждения).
- Варианты реализации:
  - Новый статус или флаг, например `resolved_pending_confirmation` и переход в `closed` по событию «пользователь подтвердил».
  - Или отдельное действие: `POST /api/tickets/{id}/confirm_resolution` (для requester/агента), после которого суппорт может закрыть или тикет автоматически переходит в closed.
- Документировать в `server/docs/TICKET_SYSTEM.md` и обновить FSM в `tickets/workflow_service.py` и `tickets/statuses.py`.

#### Разрыв API и UI (из TICKET_CRM_GAP_ANALYSIS)

- В UI почти не выведены: watchers, links, KB links, problems, change links, notification prefs, дашборды по метрикам. Бэкенд это уже умеет — нужно вывести в `ticket.js` и админскую очередь (`admin.js`).
- Устранить mojibake в `admin.js`, `tickets/handlers.py`, `websocket/agent_handler.py` (русский текст в комментариях и сообщениях).

#### Создание заявки через веб (без агента)

- Публичная очередь (`/queue`) — read-only, создания заявки без входа нет.
- Для сценария «пользователь создаёт заявку через веб» нужен либо публичный intake (форма без авторизации с последующей привязкой по email/телефону), либо отдельная страница входа для клиента и вызов `POST /api/tickets/create` с его контекстом. Сейчас создание из веб возможно только из админки/авторизованного контекста (если есть вызов create из UI — проверить в `ticket.js`/админке).

#### Единый чат через тикет

- Есть два пути: job-based (`/api/chat_start`, `chat_raise`, `chat_send`) и ticket-based (`POST /api/tickets/{id}/message`). Для «эффективного чата» стоит зафиксировать канонический путь: основная переписка — в контексте тикета; job-chat оставить только как транспорт при необходимости.

#### Legacy TicketService

- `tickets/service.py` до сих пор создаёт тикет со `status="open"` и только в state, не в БД. Убрать использование или пометить deprecated и не использовать в новых сценариях.

### Рекомендуемый порядок доработок (тикеты)

1. Исправить mojibake в серверном и админском коде.
2. Реализовать сценарий «подтверждение пользователем решения» (confirm_resolution или аналог) и закрытие только после него (или явное «закрыть без подтверждения» для админа).
3. Вывести в UI: watchers, связи, KB, problems/change, уведомления, базовые метрики.
4. Добавить публичный intake или явную точку создания заявки из веб-клиента (с учётом безопасности).
5. Регрессионные тесты на создание тикета, назначение, смену статусов, закрытие.

## Часть 2. Обновление агента (потоковое, массовое)

### Желаемый порядок (из задачи)

1. Компилирую новую версию агента, указываю путь к exe или rpm (Windows/Linux).
2. Выставляю версию агента.
3. Сервер кладёт в архив, отправляет одному агенту или всем (массовое обновление с учётом ОС агента).
4. Автоматическое обновление с чётким выводом: успех/неуспех и текст ошибки.
5. Подтверждение обновления агента.

### Что уже есть

| Компонент | Статус | Примечание |
|-----------|--------|------------|
| Загрузка билда | ✅ | `POST /api/agent_builds/upload` (multipart: file, target, channel, version, archive_type) |
| Список билдов | ✅ | `GET /api/agent_builds` (auth есть) |
| Скачивание билда | ✅ | `GET /api/agent_builds/{target}/{channel}/{version}/download` (Bearer, audit) |
| Триггер обновления на устройство | ✅ | `POST /api/devices/{device_id}/agent/update` (body: target, channel, version, restart_delay_sec) |
| Доставка команды update | ✅ | device_outbox → DeviceOutboxSender → команда `update` с download_url, sha256, size, archive_type |
| Агент: скачивание | ✅ | Streaming по HTTP (chunked), проверка SHA256/size в `orchestrator._download_file_to_path` |
| Агент: pending_update.json + exit 42 | ✅ | Launcher применяет обновление (verify, переключение версии или rollback) |
| UI: вкладка «Обновление агента» | ✅ | Выбор устройства, выбор билда (target/channel/version), кнопка «Запустить обновление», вывод operation_id после 202 |
| Операция agent_update | ✅ | Создаётся при триггере, обновляется по command_result (succeeded/failed), push в UI через push_operation_updated |

### Чего не хватает / где доработать

#### 2.1. Указание пути к exe/rpm и «выставить версию»

- **Сейчас:** загрузка только через API (curl/multipart). В админке нет формы «Загрузить билд» (выбор файла, target, channel, version, archive_type).
- **Нужно:** форма в админке (вкладка «Обновление агента» или отдельная): выбор файла, target (например windows_amd64 / linux_alt_x86_64), channel, version, archive_type, кнопка «Загрузить». После успешной загрузки — сообщение и обновление списка билдов.

#### 2.2. Массовое обновление с учётом ОС

- **Сейчас:** обновление только одного устройства за вызов; `target` передаётся в body — админ должен сам выбрать правильный билд под ОС устройства.
- **Нужно:**
  - Массовый endpoint, например `POST /api/agent/update_bulk` (body: channel, version или latest, список device_id или флаг «все онлайн»). Сервер для каждого устройства определяет target по данным устройства (см. ниже) и шлёт команду update с подходящим билдом.
  - Определение target по устройству: в `GET /api/agents` уже есть `os_type` (из metadata handshake); в `GET /api/devices` есть `os` из БД. Нужна маппинг-таблица `os_type` / `os` → `target` (например `Windows` → `windows_amd64`, `Linux` → `linux_alt_x86_64`). Если агент в handshake не присылает единообразный os_type — дописать и зафиксировать в PROTOCOL_V3 или агентской документации.
- В админке: кнопка «Обновить всех» (или выбор нескольких устройств) и выбор версии/channel; при массовом обновлении показывать список операций по устройствам.

#### 2.3. Потоковый вывод: успех/неуспех и ошибка

- **Сейчас:** после «Запустить обновление» показывается только «Обновление принято в очередь» и operation_id. Итог (succeeded/failed) приходит по command_result и уходит в UI через `push_operation_updated`, но вкладка «Обновление агента» не подписана на эти события и не обновляет результат на экране.
- **Нужно:**
  - На вкладке «Обновление агента» после триггера подписаться на обновления операции (по operation_id) через существующий WS /ws_ui или механизм подписки на операции.
  - При приходе `operation_updated` для этого operation_id обновить блок результата: «Успех» (зелёный) или «Ошибка» (красный) + текст ошибки из операции (error_code, message).
  - Аналогично для массового обновления: список операций с обновлением статуса каждой в реальном времени.

#### 2.4. Подтверждение обновления агента

- **Сейчас:** агент после применения обновления перезапускается и подключается заново; сервер видит новое подключение и версию в metadata. Явного «подтверждения обновления» (отдельное событие или поле) нет.
- **Нужно:** считать подтверждением факт успешного переподключения агента с новой версией (уже есть в handshake). При желании можно добавить отдельное событие или поле в handshake, например `last_update_operation_id` / `applied_update_version`, и выводить в админке «Агент обновлён до версии X (операция Y)».

#### 2.5. Прочие моменты

- **Стриминг:** скачивание на агенте уже потоковое (chunked), большие файлы не держатся целиком в памяти — доработок не требуется.
- **Права:** GET /api/agent_builds уже с auth; policy для update — admin. Оставить как есть.
- **Документация:** обновить `server/docs/AGENT_UPDATES_API.md` и `server/docs/AGENT_UPDATES_ANALYSIS.md` после добавления bulk API и UI (форма загрузки, потоковый результат, массовое обновление).
- **Тесты:** добавить автотест на `POST /api/devices/{device_id}/agent/update` (мок агента online, проверка outbox и операции) и при наличии — E2E на полный цикл обновления.

## Где могут быть проблемы

1. **Тикеты**
   - Две модели чата (job vs ticket) могут путать пользователей и разработчиков — зафиксировать канонический путь.
   - Сессии восстанавливаются из БД и state; при рестарте сервера нужно убедиться, что открытые тикеты и чаты не теряют контекст.
   - Legacy TicketService — риск случайно создать тикет мимо БД при новой интеграции; убрать или жёстко deprecate.

2. **Обновление агента**
   - Маппинг ОС → target может отличаться по окружениям (разные имена ОС от агента). Нужен конфигурируемый маппинг и fallback.
   - При массовом обновлении часть агентов может быть offline — обрабатывать 409 и показывать в UI «не в сети» по device_id.
   - SERVER_PUBLIC_BASE_URL должен быть доступен с устройств для download; при разных сетях — явно описать в конфиге/документации.

3. **Безопасность**
   - Не логировать полный токен при download (сейчас в агенте только префикс — ок).
   - Публичный intake для тикетов — только с продуманной верификацией (капча, лимиты, привязка к контакту).

После внесения изменений в маршруты, точки входа и ключевые потоки обновить соответствующие разделы в `server/docs/CODEMAP.md` и при необходимости `pc_agent/docs/CODEMAP.md`.
