# Анализ: параметры атомарных модулей, ОС и оболочки (PowerShell / терминал)

**Дата:** 2026-03-03

Документ анализирует: (1) атомарные модули с параметрами и выбором «по умолчанию» / пресеты; (2) модули под конкретную ОС и универсальные; (3) модули для работы с PowerShell и Linux-терминалом.

---

## 1. Атомарные модули с параметрами (default / preset)

### 1.1 Текущая поддержка в агенте

- **`@exposed_tool`** в `pc_agent/core/registry.py` поддерживает:
  - **params_schema** — JSON Schema параметров (устаревший вариант);
  - **params_model** — Pydantic-модель (рекомендуется): поля с `Field(default=...)` задают значения по умолчанию;
  - **presets** — список предустановок: `id`, `name`, `description`, `params` (словарь параметров для подстановки).

- **Вызов:** `run_tool` принимает `params: dict`. Оркестратор:
  - при наличии **params_model** валидирует `params` через Pydantic и подставляет недостающие значения из default;
  - при отсутствии params_model передаёт `params` как есть (только ключи из сигнатуры метода);
  - **preset** на стороне клиента (админка/API): клиент выбирает preset и подставляет его `params` в запрос; агент получает уже готовый словарь.

- **Пример (system.collect):** параметры `include_ip`, `include_hostname` с default `True`; пресеты «Базовые метрики», «Полная информация», «Минимальная» подставляют разные комбинации.

### 1.2 Ограничение текущего «создания из формы» (POST /api/modules/create)

- Шаблон в `server/utils/module_builder.py` генерирует инструмент **без параметров**: метод имеет вид `async def {{TOOL_NAME}}(self) -> Dict[str, Any]`, тело — только пользовательский код.
- В форме создания модуля нет полей для описания параметров (имена, типы, default) и пресетов.

### 1.3 Возможность: параметры и пресеты в атомарных модулях

**Реализуемо без смены контракта агента.**

1. **Расширение API и шаблона (рекомендуемый путь)**  
   - В **POST /api/modules/create** добавить опциональные поля, например:
     - `params_schema` — JSON Schema (или упрощённый список полей: `[{ "name": "timeout", "type": "integer", "default": 5 }]`);
     - `presets` — массив `[{ "id": "...", "name": "...", "description": "...", "params": { ... } }]`.
   - В **шаблоне** генерировать:
     - метод с аргументами по схеме и значениями по умолчанию (например через `**kwargs` и извлечение из `params` в теле);
     - вызов `@exposed_tool(..., params_schema=..., presets=...)` (и при необходимости params_model, если на сервере генерировать Pydantic-модель не хочется — достаточно params_schema).
   - При запуске инструмента:
     - **по умолчанию:** если клиент не передаёт `params` или передаёт `{}`, агент использует default из params_schema/params_model.
     - **смена параметра:** клиент передаёт в `params` нужные ключи (частичная подстановка; остальное — из default).
     - **выбор пресета:** клиент (веб или API) выбирает preset и подставляет его `params` в запрос к `run_tool`; агент снова получает полный словарь.

2. **Только пресеты без явной схемы**  
   Можно поддерживать только `presets`: в форме задаётся несколько вариантов (имя + params), в шаблоне — метод с `**kwargs` и `@exposed_tool(..., presets=...)`. «По умолчанию» — первый пресет или пустой `params`.

3. **Валидация**  
   При наличии params_schema агент уже может валидировать входящие params (через существующую логику с params_model или добавив валидацию по JSON Schema). Сообщения об ошибках возвращать в command_result.

**Итог:** при запуске атомарного модуля можно либо менять параметры (передавая их в `params`), либо выбирать «по умолчанию» (пустой или дефолтный набор) или пресет (подстановка на стороне клиента). Для этого нужно расширить форму/API создания модуля и шаблон генерации `module.py`.

## 2. Модули под конкретную ОС и универсальные

### 2.1 Текущее состояние

- **Handshake агента** передаёт в payload, в т.ч., `os` и `os_version` (например через `platform.system()` / `platform.release()`), сервер может сохранять это в БД (устройство).
- **Модули** при установке не фильтруются по ОС: один и тот же ZIP ставится на все агенты. Проверки «только Windows» / «только Linux» в установщике нет.
- **Зависимости:** в `manifest.json` есть опциональные поля `requirements`, `optional_requirements`; агент **не** устанавливает пакеты при установке модуля — окружение общее (тот же интерпретатор). На Windows и Linux набор установленных пакетов может отличаться.

### 2.2 Возможность: модули под конкретную ОС

**Варианты.**

1. **Поле в manifest (рекомендуемый минимум)**  
   - Добавить в manifest, например, `"platforms": ["linux", "win32"]` или `"platforms": ["any"]`.
   - При **установке** на агенте: считать `platform.system().lower()` (или аналог) и проверять вхождение в `platforms`; если модуль не для этой ОС — не устанавливать / вернуть ошибку с понятным сообщением.
   - На **сервере** при отображении списка модулей и при выборе устройств для установки можно показывать предупреждение или фильтр «под текущую ОС устройства» (если известна из БД).

2. **Разные пакеты под ОС**  
   - Один и тот же «логический» модуль — разные ZIP (например `mymodule_win.zip` и `mymodule_linux.zip`) с разным кодом или зависимостями. Тогда версионирование и имена нужно согласовать (например суффикс в имени или отдельные module_name); установка — по правилу выше по `platforms` в manifest.

3. **Универсальные модули**  
   - Код внутри модуля сам проверяет ОС (`sys.platform`, `platform.system()`) и ветвит логику или возвращает ошибку «не поддерживается на этой ОС». Manifest можно не расширять; при желании в manifest указать `"platforms": ["any"]` и документировать поведение в описании модуля.

**Итог:** возможность есть: расширить manifest полем `platforms`, на агенте при установке проверять ОС; универсальные модули — либо без ограничения, либо с явной пометкой и ветвлением внутри кода.

## 3. Модули для PowerShell (Windows) и терминала Linux

### 3.1 Общая идея

- Модуль предоставляет инструмент, который внутри выполняет команду во внешней оболочке:
  - **Windows:** PowerShell (например `powershell.exe -NoProfile -Command "..."` или скрипт).
  - **Linux (и при необходимости macOS):** `/bin/sh` или конкретный shell (`bash`, `zsh`), например через `subprocess` с `shell=True` или явным `executable`.
- Параметры инструмента: как минимум строка команды (или скрипт + аргументы); опционально таймаут, кодировка, рабочий каталог.

### 3.2 Риски и ограничения

- **Безопасность:** выполнение произвольных строк от пользователя/админа — высокий риск. Такие инструменты должны быть с высоким `risk_level` (например `dangerous`), требовать согласие и/или ограничение по ролям (только admin).
- **Инъекции:** команда не должна подставляться в shell «как есть» без экранирования; предпочтительно передавать аргументы списком (без `shell=True`) где возможно.
- **Платформа:** на агенте без Windows PowerShell недоступен; на Windows вызов `subprocess` с `powershell.exe` возможен. Нужна проверка ОС внутри модуля или отдельные модули/версии под Windows и Linux.

### 3.3 Реализация на агенте (Python)

- **PowerShell (Windows):**
  - Запуск: `subprocess.run(["powershell.exe", "-NoProfile", "-NonInteractive", "-Command", script], capture_output=True, timeout=..., cwd=...)`.
  - Либо `-File script.ps1` с аргументами. Кодировка: явно задать UTF-8 при необходимости.
- **Терминал Linux:**
  - Вариант 1: `subprocess.run(["/bin/sh", "-c", command], capture_output=True, timeout=..., cwd=...)`.
  - Вариант 2: `subprocess.run(command.split(), ...)` без shell — только для одной команды без пайпов/перенаправлений.
- Результат: stdout/stderr, returncode; в observations модуля вернуть текст вывода и код возврата.

### 3.4 Возможность в рамках атомарных модулей

- **Отдельные модули (рекомендуется):** например `powershell_run` (только Windows) и `shell_run` (Linux/macOS) с параметрами: команда/скрипт, таймаут, cwd. В manifest указать `platforms: ["win32"]` и `["linux","darwin"]` соответственно.
- **Универсальный модуль «run shell»:** один модуль с ветвлением по `sys.platform`: на Windows — PowerShell, на Linux — sh/bash. В manifest `platforms: ["any"]`; в описании указать различие поведения по ОС.
- **Создание из формы:** текущая форма «только тело функции» не запрещает вызывать в коде `subprocess`; пользователь может вставить вызов PowerShell/sh. Но тогда параметры (команда, таймаут) нужно либо захардкодить в теле, либо расширить форму/шаблон параметрами (см. п. 1). Для безопасного шаблона «run command» лучше отдельный тип модуля или явные параметры (command, timeout_sec) с проверкой прав и risk_level.

**Итог:** возможность есть; реализуется модулями, которые внутри вызывают `subprocess` к PowerShell или sh; обязательны ограничение по ОС (или ветвление), высокий risk_level и по возможности — явные параметры вместо произвольного кода в форме.
