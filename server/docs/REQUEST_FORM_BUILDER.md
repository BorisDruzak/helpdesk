# Конструктор форм заявок

Документ описывает рабочий сценарий администратора для каталога входящих заявок `request_forms`.

## Зачем нужен конструктор

Конструктор управляет типовыми формами, которые видят:

- пользователь на странице `/help`;
- локальный агент при создании заявки;
- сервер при валидации `form_key`, `form_payload` и `ticket_type`.

Цель конструктора — собирать понятные формы без ручного редактирования JSON и без лишних вопросов на входе.

## Основные сущности

- Каталог форм: versioned pack с `pack_key`, `version`, `title`, `description`, `forms`.
- Форма: тип заявки с `key`, `request_kind`, `title`, `description`, `fields`.
- Поле: элемент формы с `key`, `label`, `type`, `required`, `placeholder`, `help_text`, `options`, `visible_when`.

## Обычный сценарий администратора

### 1. Создать новую форму

Используйте отдельный пошаговый сценарий `Создать форму`.

На простом пути администратор заполняет только:

- название формы;
- системный ключ формы;
- список полей;
- системные ключи полей.

Дополнительные параметры должны быть спрятаны в `Расширенные настройки`.

### 2. Добавить поля

Для каждого поля в базовом сценарии нужны:

- название поля;
- ключ поля;
- тип поля;
- обязательность.

Если тип поля `select` или `radio`, редактор должен запросить список вариантов.

### 3. Проверить и добавить в каталог

Перед публикацией администратор должен увидеть:

- краткую сводку по форме;
- список предупреждений, если что-то не заполнено;
- объяснение, что добавление формы в каталог ещё не публикует новую версию.

### 4. Сохранить версию каталога

Публикация каталога — отдельный шаг в разделе `Каталог`.

Администратор задаёт:

- версию;
- короткое описание изменений;
- при необходимости флаг `сделать активной`.

## Что считается расширенными настройками

Эти параметры не должны мешать базовому сценарию и должны быть скрыты под `details/summary` или отдельным advanced-блоком:

- `description` формы;
- `request_kind`, если он отличается от `key`;
- `placeholder`;
- `help_text`;
- `visible_when`;
- raw JSON preview.

## Правила ключей

- Используйте латиницу, цифры и `_`.
- Для форм придерживайтесь коротких semantic key: `printer`, `access`, `site_system`.
- Для полей придерживайтесь snake_case: `printer_model`, `system_name`, `affected_scope`.
- Если `request_kind` не переопределён, он должен совпадать с `key`.

## Подсказки, которые должны быть в UI

Интерфейс должен объяснять:

- разницу между `создать форму` и `сохранить версию каталога`;
- что ключи нужны для API и аналитики;
- что сложные условия показа доступны в расширенных настройках;
- что после изменения каталога нужно сохранить новую версию, иначе агент и `/help` не увидят изменения.

## Где используется этот контракт

- UI администратора: `server/admin_ticket_forms_builder.html`, `server/admin_ticket_forms_builder.js`, `server/admin.html`
- Серверная валидация и default pack: `server/tickets/form_catalog.py`
- HTTP API pack registry: `server/tickets/form_pack_handlers.py`
- Публичная форма: `server/help.html`, `server/help.js`
- Агентский диалог создания тикета: `pc_agent/ui_gui/chat_panel.py`
