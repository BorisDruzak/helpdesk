# Установка модулей: сложности, узкие места и реализованные решения

Документ описывает проблемы при установке модулей и **реализованные** решения (откат при сбое, авто-sync, состояние failed на сервере).

**Дата:** 2026-02-22

## Реализовано (2026-02-22)

1. **Откат при сбое установки/загрузки (агент)**  
   Если после распаковки модуля сбой при активации или загрузке (load_module_from_path) — агент удаляет каталог модуля с диска (`remove_version_force`). Нерабочий модуль не остаётся «установленным», решается проблема зависших модулей и конфликта SHA при следующей установке.

2. **Удаление сломанных модулей при пересборке реестра и при старте (агент)**  
   В `_rebuild_registry_from_active_modules()` и в автозагрузке из modules_store при старте: если модуль не загружается (исключение при load_module_from_path), он удаляется с диска через `remove_version_force`. Состояние «на диске есть, в registry нет» не накапливается.

3. **Автосинхронизация после успешной установки (сервер)**  
   При успешном `command_result` для `install_module_package` сервер ставит в очередь команды `list_installed_modules` и `list_tools` для этого устройства. Ручной вызов sync после установки не обязателен.

4. **Корректное состояние failed при ошибке установки (сервер)**  
   При `command_result` с ошибкой для `install_module_package` сервер создаёт/обновляет запись в `device_modules` с `installed=False`, `active=False`, `state="failed"`, `last_error_code` и `last_error_message` (через `upsert_device_module`), а не только `mark_error` по существующей записи.

## 1. Конфликт SHA при переустановке той же версии (INSTALL_CONFLICT_SHA)

### Что происходит

- Модуль залили на сервер с исправлениями под тем же **именем и версией** (например, os_check 1.0.0), но с **другим SHA256** архива.
- Агент уже имел старую сборку os_check 1.0.0 (другой SHA).
- При установке агент в `ModuleManager.install_zip_bytes()` проверяет: если каталог `modules_store/<name>/<version>` уже есть и файл `.sha256` содержит другой хеш — выбрасывается **INSTALL_CONFLICT_SHA**, установка не выполняется.
- Пользователю приходится вручную: удалить старую версию (remove_version/remove_module), дождаться выполнения, затем ставить заново. Либо поднимать версию (1.0.1) и ставить её как новую.

**Код:** `pc_agent/core/module_manager.py`, строки 116–136 (проверка `target_path.exists()` и сравнение `current_sha` с `actual_sha256`).

### Предложения

1. **Вариант A (агент): «Replace if different SHA»**  
   В команде `install_module_package` добавить опциональный параметр, например `replace_if_different_sha: true`.  
   В `install_zip_bytes()` при конфликте SHA:
   - если `replace_if_different_sha` задан — удалить существующий каталог `target_path` и продолжить установку (как при первой установке);
   - иначе — оставить текущее поведение (ошибка INSTALL_CONFLICT_SHA).

2. **Вариант B (агент): автоматическая замена по умолчанию**  
   Без нового параметра: при том же (name, version) и другом SHA считать установку «обновлением» — удалить старый каталог и установить новый пакет. Идемпотентность сохраняется для случая «тот же SHA» (уже реализовано).

3. **Вариант C (сервер): «force» или «replace» при install**  
   В `POST /api/devices/{device_id}/modules/install` добавить тело, например `"replace_if_exists": true`. Сервер при формировании команды агенту передаёт соответствующий флаг в params (например, `replace_if_different_sha`), агент ведёт себя как в A или B.

Рекомендация: **A + C** — явный флаг на сервере и агенте, чтобы не ломать текущее строгое поведение для тех, кто полагается на «та же версия = тот же контент».

## 2. Невозможность удаления модуля при отсутствии в inventory сервера

### Что происходит

- На агенте на диске есть модуль (например, остался от прошлой установки или после сбоя).
- В таблице `device_modules` на сервере записи по этому модулю для данного устройства **нет** (например, синхронизация не выполнялась или запись была удалена).
- Вызовы `POST .../modules/remove_version` и `POST .../modules/remove` возвращают **400** с текстом вроде: «Module … not found in device inventory. Sync modules first.»

В результате пользователь не может отправить агенту команду «удали этот модуль», пока сервер не «увидит» модуль в inventory. Приходится сначала делать sync, ждать, потом remove.

**Код:** `server/modules/handlers.py`: для remove_version — проверка по `get_device_modules` и `found` (строки 1433–1442); для remove — аналогично (1514–1521).

### Предложения

1. **Разрешить remove без проверки inventory (force remove)**  
   Добавить в тело запроса опцию, например `"force": true`.  
   При `force: true` не проверять наличие модуля в `device_modules`, а сразу создавать operation и ставить в outbox команду `remove_module_version` / `remove_module`. Агент выполнит удаление, если модуль есть на диске; если нет — команда станет no-op.  
   Это упрощает сценарии «почисти агента» и «переустанови с новым SHA» без обязательного предварительного sync.

2. **Опционально: отдельный endpoint**  
   Например, `POST .../modules/remove_force` с телом `{"module_name": "...", "version": "..."}` без проверки inventory — только enqueue команды агенту.

Рекомендация: **п. 1** — один endpoint с флагом `force`, чтобы не раздувать API.

## 3. Расхождение состояния «установлен / активен» и реальной загрузки модуля

### Что происходит

- В `device_modules` модуль может быть в состоянии **active** (по результатам `list_installed_modules` или по успешному `install_module_package` в прошлом).
- На агенте модуль при загрузке мог упасть (например, ImportError: `No module named 'pc_agent.core.registry'`). В registry инструменты этого модуля не попадают.
- В итоге: в UI/API модуль «установлен и активен», но в toolset (list_tools) его инструментов нет, вызов run_tool даёт «инструмент не найден».

Пользователь не понимает, что проблема в ошибке загрузки на агенте, а не в том, что «модуль не установлен».

### Предложения

1. **Корректно отражать результат установки на сервере**  
   При получении `command_result` по операции `install_module_package`: если статус **failed** (в т.ч. из-за ошибки загрузки после распаковки), обновлять запись в `device_modules` в состояние **failed** и сохранять `last_error_code` / `last_error_message`, а не помечать модуль как active.

2. **Состояние «loaded» vs «installed»**  
   Опционально: разделить «установлен на диск» и «успешно загружен в registry». Например, после успешного `install_zip_bytes` и попытки активации агент мог бы присылать отдельное событие/флаг «module_loaded» / «module_load_failed» с причиной. Сервер тогда мог бы показывать в UI «установлен, но не загружен (ошибка: …)».

3. **Sync после install**  
   После успешной установки сервер может автоматически ставить в очередь sync (list_installed_modules + list_tools) для этого устройства, чтобы toolset и inventory обновились без ручного вызова sync пользователем.

Рекомендация: минимум — **п. 1**; при возможности — **п. 3** для более предсказуемого обновления списка инструментов после установки.

## 4. Многошаговый сценарий и долгое ожидание

### Что происходит

- Типичный сценарий: загрузка модуля (upload) → установка (install) на N устройств → ожидание 10–20 секунд → sync → ещё ожидание → проверка toolset / вызов инструмента.
- Каждый шаг — отдельный HTTP-запрос; результат установки асинхронный (202 + operation_id), пользователь вынужден сам опрашивать статус операции или ждать «на глаз».
- При конфликте SHA добавляются шаги: sync → remove (или remove_version) → ожидание → install → снова ожидание.

### Предложения

1. **Опциональный синхронный режим install**  
   В `POST .../modules/install` добавить query-параметр, например `?wait=1` или тело `"wait_completion": true` с таймаутом (например, 60–90 сек). Сервер после постановки команды в outbox ждёт завершения операции (успех/ошибка) и возвращает 200 с итогом (status, error_code, error_message при ошибке) вместо 202. Это упрощает скрипты и автоматизацию.

2. **Единый «deploy» endpoint (оркестрация на сервере)**  
   Например, `POST /api/devices/{device_id}/modules/deploy` с телом: `module_name`, `version`, опционально `replace_if_exists`, опционально `wait_completion`.  
   Сервер сам: при необходимости выполняет «логическое» удаление старой версии (если replace и есть запись в device_modules), ставит install, при `wait_completion` ждёт результат и при необходимости инициирует sync. Один вызов вместо нескольких.

3. **Массовая установка**  
   `POST /api/modules/bulk_install` с телом `{"module_name": "...", "version": "...", "device_ids": ["...", "..."]}` — создаёт операции установки для всех перечисленных устройств и возвращает список operation_id. Опционально — с `wait_completion` и таймаутом (тогда ждать завершения на всех устройствах или по таймауту вернуть частичный результат).

Рекомендация: сначала **п. 1** (wait_completion для install), затем при необходимости **п. 2** для упрощения сценария «переустановить/обновить один модуль на одном агенте».

## 5. Формат имени инструмента (module.tool)

### Что происходит

- Вызов run_tool с `tool_name: "get_os_info"` возвращает ошибку: «Используйте формат "module.tool" (например ping_check.ping_host). Короткое имя не поддерживается.»
- Пользователь должен знать или угадывать префикс модуля и вызывать `os_check.get_os_info`.

### Предложения

1. **Документация и примеры**  
   В описании Admin API (run_tool) и в UI явно указать: инструменты вызываются в формате `module_name.tool_name` (например, `os_check.get_os_info`). Добавить примеры в README и в ответы ошибок.

2. **Разрешить короткое имя при однозначности**  
   Если передан только `tool_name` без точки, сервер/агент при наличии ровно одного инструмента с таким именем (в любом модуле) могут подставлять полное имя `module.tool`. При неоднозначности — 400 с перечислением подходящих `module.tool`.

Рекомендация: минимум **п. 1**; **п. 2** — по желанию для удобства.

## 6. Краткая сводка приоритетов

| # | Проблема | Где менять | Приоритет |
|---|----------|------------|-----------|
| 1 | INSTALL_CONFLICT_SHA при обновлении той же версии | Агент: module_manager + оркестратор (флаг replace). Сервер: install handler (query/body force/replace). | Высокий |
| 2 | Remove невозможен без записи в device_modules | Сервер: remove/remove_version — опция force, не проверять inventory. | Высокий |
| 3 | Состояние «active» при ошибке загрузки модуля | Сервер: при failed command_result по install не ставить active, писать failed + error_message. | Средний |
| 4 | Долгое ожидание и много шагов | Сервер: wait_completion для install; опционально deploy endpoint и bulk_install. | Средний |
| 5 | Неочевидный формат module.tool | Документация, ошибки; опционально резолв короткого имени. | Низкий |

Внедрение пунктов 1 и 2 уже существенно упростит переустановку и обновление модулей без ручного подъёма версии и без обязательного sync перед remove.
