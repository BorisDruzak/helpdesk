# Registry Platform Commands and Eligibility API v1

Status: PR-9 prerequisite and acceptance contract. This describes the minimum
external Registry Platform interface before Helpdesk may change command or
authentication eligibility authority. It is not a Helpdesk route, transport
implementation, feature-flag change, or deployment instruction.

## Authority boundary and activation gate

- Until this contract has external service acceptance evidence for every
  operation being enabled, Helpdesk command and eligibility authority remains
  local/off. `REGISTRY_PORT_MODE=local` remains the effective authority and no
  runtime authority change is authorized by this document.
- `ui_users`, Helpdesk web sessions, UI tokens and RBAC remain Helpdesk-owned.
  Registry may decide eligibility or return a command result, but it must not
  create, modify or authorize a Helpdesk user, web session, token or role.
- Tickets and `user_consent_requests` remain Helpdesk-owned. Their immutable
  ticket and consent references are opaque historical evidence, never an
  authorization substitute and never a Registry foreign key.
- A later authority cutover must be one operation at a time, explicitly flag
  gated, with the previous local path disabled for that operation. There is no
  local fallback after an external operation flag is on.

## Common transport, identity and result envelope

All paths are rooted at `https://<registry-platform>/v1/helpdesk`. Every call
uses HTTPS service authentication: `Authorization: Bearer <service-token>` and
the command-specific `X-Registry-Service-Scope`. The Registry service validates
the caller identity and scope before reading the command payload. Both services
must never log raw tokens, authorization headers, credentials, pairing codes,
session delivery values or request/response bodies.

Each command requires these trusted inputs:

- `actor`: authoritative actor authorization context built from verified
  Helpdesk authentication, including opaque actor reference, actor kind and
  verified roles/scopes. Browser, agent or HTTP payload claims never replace
  it.
- `operation_id`: an opaque stable idempotency key generated by the caller and
  unique for the semantic command. It must not be reused for a different
  request body or actor.
- `correlation_id`: a fresh opaque correlation ID for diagnostics and tracing;
  it is distinct from `operation_id` and must not be exposed to untrusted UI.

The Registry persists an idempotency record before side effects. A replay with
the same authenticated caller and semantically identical request returns the
same terminal result; a reused key with different request semantics returns
`registry_idempotency_conflict`. It must never repeat a mutation, create a
second session, or deliver a second pairing result. Responses echo only opaque
`operation_id` and `correlation_id` plus redacted result data.

Typed errors are part of the command result, not transport fallbacks:

- `registry_unavailable`: timeout, network failure, service outage or disabled
  service integration. Helpdesk must fail closed and must not infer success.
- `registry_unauthorized`: service scope, trusted actor authorization or
  operation eligibility was rejected. It is never retried with weaker context.
- `registry_operation_uncertain`: a command may have reached Registry but its
  terminal outcome cannot be proven. Helpdesk must fail closed, persist only
  safe operation evidence, and retry only the same `operation_id`.
- `registry_invalid_request`, `registry_not_found` and
  `registry_idempotency_conflict`: deterministic terminal errors; no local
  fallback or shadow write is permitted.

## Eligibility and command surface

Each command accepts the common inputs and must return an idempotent terminal
acknowledgement with a safe status/code. The external Registry service must
prove each listed acceptance item in an environment separate from Helpdesk
production before the matching authority flag can be enabled.

| Operation | v1 endpoint | Required acceptance evidence |
| --- | --- | --- |
| UI-login eligibility | `POST /eligibility/ui-login` | Verified `ui_login` identity is evaluated against the authoritative actor and active binding; denied, unavailable and uncertain outcomes fail closed; it does not issue a Helpdesk web session. |
| Registration request | `POST /commands/registrations` | Replaying `operation_id` creates one request only; returned request reference is opaque; requester self-report never grants a binding. |
| Registration approve / reject | `POST /commands/registrations/{registration_ref}/approve` and `/reject` | Actor scope and reason are audited; conflicting or repeated decisions yield the saved terminal result without duplicate events. |
| Binding bind / revoke | `POST /commands/bindings` and `POST /commands/bindings/{binding_ref}/revoke` | Actor eligibility, device/person ownership and existing binding state are evaluated by Registry; duplicate calls cannot create or revoke more than once. |
| Session create / validate / logout / revoke | `POST /commands/sessions`, `POST /commands/sessions/{session_ref}/validate`, `/logout`, `/revoke` | Every session result is device-scoped and durable; validation rechecks current eligibility; a replay is deterministic and does not mint another session. |
| Browser pairing create / lookup / confirm / pickup | `POST /commands/browser-pairings`, `POST /commands/browser-pairings/lookup`, `POST /commands/browser-pairings/{pairing_ref}/confirm`, `POST /commands/browser-pairings/{pairing_ref}/pickup` | Pairing code is never returned in logs or diagnostics; confirm/pickup are scoped to the verified actor/device; durable one-time pickup acknowledgement proves exactly-once delivery of a pairing/session result across retry, restart and worker change. |
| Other-account approval | `POST /commands/other-account-requests/{request_ref}/approve` | Approver role and device/request scope are checked in Registry; the terminal result creates at most one eligible, device-scoped session and does not alter Helpdesk RBAC. |

`lookup` is a read-like step but remains in this command contract because it
handles an expiring pairing capability. It is subject to the same trusted actor,
correlation, redaction and fail-closed rules. No command may perform a shadow
write; command comparisons never authorize a result.

## Preflight and per-operation cutover record

Before enabling an operation, the external service acceptance evidence must
include all of the following, stored as a redacted release artifact:

1. HTTPS certificate/hostname and service authentication scope probe.
2. Authorized and unauthorized actor cases, including explicit
   `registry_unauthorized` evidence.
3. First call, same-key replay, conflicting-key replay and timeout/uncertain
   result cases with a single observable side effect.
4. Correlation traceability without raw token, secret, pairing or session
   values in logs.
5. For session and pairing pickup, restart/retry evidence proving exactly-once
   delivery and durable terminal acknowledgement.
6. Fail-closed `registry_unavailable` and `registry_operation_uncertain`
   behavior in Helpdesk, with no local fallback once the operation flag is on.
7. A rollback decision that disables only the new operation flag; it does not
   delete Registry records or restore a potentially uncertain command locally.

The acceptance record must name the exact operation, contract version, service
build, test environment, timestamps, redacted evidence locations and rollback
owner. It is a prerequisite for Task 8; this document alone grants no runtime
authority and does not make external endpoints active.

## Non-goals

This contract does not add external endpoints to Helpdesk, alter
`REGISTRY_PORT_MODE`, migrate schema, delete local Registry data, or deploy a
service. Browser smoke and production acceptance remain separate release gates.
